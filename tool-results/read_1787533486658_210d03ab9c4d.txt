    41→### 1.1 Tech Stack (Battle-Tested Defaults)
    42→
    43→| Layer | Choice | Why |
    44→|-------|--------|-----|
    45→| Framework | Next.js 16 (App Router) | Server Components, RSC streaming, standalone output |
    46→| Language | TypeScript 5 (strict) | Catches ~70% of bugs at compile time |
    47→| Styling | Tailwind CSS 4 + shadcn/ui | Utility-first, no CSS-in-JS runtime |
    48→| Database | Prisma 6 + SQLite (dev) / PostgreSQL (prod) | Type-safe queries, migrations |

    51→| State | Zustand (client) + TanStack Query (server) | Minimal boilerplate |
    52→| 3D/Heavy | Three.js via `dynamic(() => import(...), { ssr: false })` | Never ship to SSR |

    99→### 1.3 Next.js 16 Specifics (Critical — These Changed)
   100→
   101→#### `params` and `searchParams` are now Promises
   102→In Next.js 16, every page that receives `params` or `searchParams` MUST await them. The old
   103→synchronous signature silently breaks or causes type errors.
   104→
   105→```tsx
   106→// ✅ CORRECT (Next.js 16)
   107→export default async function ProductPage({
   108→  params,
   109→}: {
   110→  params: Promise<{ locale: string; slug: string }>
   111→}) {
   112→  const { locale, slug } = await params
   113→  // ...
   114→}
   115→
   116→// ❌ WRONG (Next.js 15 and earlier — will break)
   117→export default function ProductPage({ params }: { params: { slug: string } }) {
   118→  const { slug } = params
   119→}
   120→```
   121→
   122→#### `proxy.ts` replaces `middleware.ts`
   123→Next.js 16 renamed `middleware.ts` to `proxy.ts`. **Never** create `src/middleware.ts` — it
   124→will conflict with `proxy.ts` and cause build failures. If you see a stale `middleware.ts`,
   125→delete it and add it to `.gitignore`.
   126→
   127→#### `cookies()` and `headers()` are now async
   128→Since Next.js 15, `cookies()` and `headers()` (from `next/headers`) return Promises. You must
   129→`await` them — calling `.get()` on the Promise directly is a type error and a runtime crash:
   130→
   131→```ts
   132→import { cookies } from 'next/headers'
   133→
   134→// ✅ CORRECT
   135→const store = await cookies()
   136→const session = store.get('session')
   137→
   138→// ❌ WRONG (Next.js 14 style — breaks on 15+)
   139→const session = cookies().get('session')
   140→```
   141→
   142→Note: `store.set()` only works inside Server Actions and Route Handlers — never during a
   143→page render.
   144→
   145→#### `global-error.tsx` location
   146→`global-error.tsx` is only honored at `src/app/global-error.tsx` (the root). Placing it
   147→inside `[locale]/` makes it dead code. It must render its own `<html>` and `<body>`:
   148→
   149→```tsx
   150→'use client'
   151→export default function GlobalError({ error, reset }: { error: Error; reset: () => void }) {
   152→  return (
   153→    <html lang="en">
   154→      <body>
   155→        <h2>Something went wrong!</h2>
   156→        <button onClick={() => reset()}>Try again</button>
   157→      </body>
   158→    </html>
   159→  )
   160→}
   161→```
   162→
   163→### 1.4 Route Group Pitfalls
   164→
   165→Route groups `(name)` do NOT affect the URL. Two files at the same effective path cause a
   166→build-time "two parallel pages that resolve to the same path" error:
   167→
   168→```
   169→src/app/[locale]/admin/page.tsx              → /admin
   170→src/app/[locale]/admin/(dashboard)/page.tsx  → /admin   ← CONFLICT!
   171→```
   172→
   173→**Rule**: Only ONE page.tsx may resolve to any given URL. Use route groups for layout
   174→grouping, not for alternate page content. If you need a "landing vs dashboard" split,
   175→redirect from one to the other:
   176→
   177→```tsx
   178→// src/app/[locale]/admin/page.tsx
   179→import { redirect } from 'next/navigation'
   180→export default function AdminEntry() {
   181→  redirect('/admin/dashboard')  // or to login if unauthenticated
   182→}
   183→```
   184→
   185→### 1.5 Server vs Client Component Boundaries
   186→
   187→Mark a component `'use client'` ONLY when it needs:
   188→- `useState`, `useEffect`, `useReducer`, context
   189→- Event handlers (`onClick`, etc.)
   190→- Browser APIs (`window`, `localStorage`, `navigator`)
   191→- `usePathname`, `useRouter`, `useSearchParams`
   192→
   193→**Anti-pattern**: A `'use client'` component that imports `@/lib/db` or `fs`. This bloats
   194→the client bundle and leaks server code. Instead, fetch data in a server component and pass
   195→it as serializable props to a client child.
   196→
   197→**Anti-pattern**: A server component using hooks. It will crash at runtime.
   198→
   199→**Heavy library rule**: Three.js, Chart.js, and any library >50KB should be dynamically
   200→imported with `{ ssr: false }` when used in client components:
   201→
   202→```tsx
   203→const Heavy3D = dynamic(() => import('./heavy-3d'), {
   204→  ssr: false,
   205→  loading: () => <div className="fixed inset-0 -z-10 bg-background" />, // ← NEVER null
   206→})
   207→```
   208→
   209→### 1.6 Hydration Safety
   210→
   211→Anything that differs between server and client renders causes a hydration mismatch
   212→warning (or crash). The classic traps:
   213→
   214→| Trap | Fix |
   215→|------|-----|
   216→| `Date.now()`, `Math.random()` in render | Move to `useEffect` |
   217→| `typeof window !== 'undefined'` checks | Use `useEffect` + state instead |
   218→| `localStorage` / `sessionStorage` in render | Gate with `useEffect` + `mounted` state |
   219→| Timezone-dependent date formatting | Format on the client only, after mount |
   220→| `window.matchMedia('(prefers-reduced-motion)')` in render | Use a `mounted` flag |
   221→
   222→```tsx
   223→// ✅ Safe hydration guard pattern
   224→const [mounted, setMounted] = useState(false)
   225→useEffect(() => setMounted(true), [])
   226→if (!mounted) return <Skeleton />  // server + first paint
   227→return <RealContent />              // client only
   228→```
   229→
   230→### 1.7 Layout Hierarchy & Sticky Footer
   231→
   232→The root locale layout MUST establish the sticky-footer pattern so short pages push the
   233→footer to the viewport bottom and long pages push it down naturally:
   234→
   235→```tsx
   236→// src/app/[locale]/layout.tsx
   237→<body className="min-h-screen flex flex-col">
   238→  <Navbar />
   239→  <main className="flex-1">{children}</main>
   240→  <Footer className="mt-auto" />
   241→</body>
   242→```
   243→
   244→- `min-h-screen flex flex-col` on the body makes it at least viewport-height and a flex column.
   245→- `flex-1` on `<main>` grows to fill available space.
   246→- `mt-auto` on `<footer>` pushes it to the bottom when content is short.
   247→- For iOS safe area: add `pb-[env(safe-area-inset-bottom)]` to the footer.
   248→
   249→### 1.8 Loading, Error, and Not-Found Files
   250→
   251→Every route segment that does async work should have:
   252→- `loading.tsx` — skeleton or spinner with `role="status"` + `aria-live="polite"` + `sr-only` text
   253→- `error.tsx` — user-friendly message + retry button (never show stack traces)
   254→- `not-found.tsx` — for 404s specific to this segment
   255→
   256→```tsx
   257→// loading.tsx
   258→export default function Loading() {
   259→  return (
   260→    <div role="status" aria-live="polite" className="flex items-center justify-center py-20">
   261→      <Loader2 className="size-6 animate-spin" />
   262→      <span className="sr-only">Loading…</span>
   263→    </div>
   264→  )
   265→}
   266→```
   267→
   268→```tsx
   269→// not-found.tsx (server component — use getTranslations, NOT useTranslations)
   270→import { getTranslations } from 'next-intl/server'
   271→export default async function NotFound() {
   272→  const t = await getTranslations()
   273→  return <h1>{t('notFound.title')}</h1>
   274→}
   275→```
   276→
   277→> **Critical pitfall**: `not-found.tsx` renders when `notFound()` is called, which can happen
   278→> BEFORE the i18n provider is mounted (e.g., invalid locale). Using `useTranslations()` (a
   279→> client hook) in a server `not-found.tsx` will throw. Always use `getTranslations()` (the
   280→> server-side async version).

   284→## 2. Security Hardening
   285→
   286→### 2.1 Authentication Architecture
   287→
   288→Use a **two-layer defense-in-depth** model:
   289→
   290→1. **Edge layer** (`src/proxy.ts`): HMAC-verified session cookie check. Runs before SSR.
   291→   Redirects unauthenticated users to `/login` for admin routes.
   292→2. **Server layer** (`requireAuth()` in every server action / admin page): Re-verifies the
   293→   session in Node. This catches any edge-layer bypass and is your real source of truth.
   294→
   295→```ts
   296→// src/lib/auth.ts
   297→import { cookies } from 'next/headers'
   298→
   299→export async function requireAuth() {
   300→  const store = await cookies()          // cookies() is async since Next.js 15
   301→  const session = store.get('session')
   302→  if (!session) throw new Error('UNAUTHORIZED')
   303→  const payload = await verifySession(session.value)  // HMAC verify
   304→  if (!payload) throw new Error('INVALID_SESSION')
   305→  return payload  // { userId, role, brand, ... }
   306→}
   307→```
   308→
   309→**Rule**: Every admin server action MUST call `requireAuth()` as its first statement. No
   310→exceptions. Do not rely on "the layout checks it" — defense in depth.
   311→
   312→### 2.2 Input Validation
   313→
   314→Validate EVERY API input before it reaches Prisma. Use Zod:
   315→
   316→```ts
   317→import { z } from 'zod'
   318→
   319→const CreateOrderSchema = z.object({
   320→  items: z.array(z.object({
   321→    productId: z.string().min(1),
   322→    quantity: z.number().int().positive().max(100),
   323→    startDate: z.string().datetime(),
   324→    endDate: z.string().datetime(),
   325→  })).min(1).max(50),
   326→  customerName: z.string().min(2).max(100),
   327→  customerPhone: z.string().min(5).max(20),
   328→})
   329→
   330→export async function POST(req: Request) {
   331→  const body = await req.json()
   332→  const parsed = CreateOrderSchema.safeParse(body)
   333→  if (!parsed.success) {
   334→    return NextResponse.json({ error: 'invalid_input', details: parsed.error.flatten() }, { status: 400 })
   335→  }
   336→  // Use parsed.data — it's now type-safe and validated
   337→}
   338→```
   339→
   340→### 2.3 SQL/NoSQL Injection
   341→
   342→Prisma's query builder is parameterized by default — safe from injection. The danger zones:
   343→
   344→- `Prisma.raw()` / `$queryRawUnsafe()` — NEVER interpolate user input.
   345→- Dynamic `orderBy` from user input — validate against an allow-list.
   346→- Dynamic field names in `select`/`where` — validate against an allow-list.
   347→
   348→```ts
   349→// ❌ DANGEROUS
   350→const orderBy = req.nextUrl.searchParams.get('sort')!
   351→const products = await db.product.findMany({ orderBy: { [orderBy]: 'asc' } })
   352→
   353→// ✅ SAFE
   354→const ALLOWED_SORTS = ['name', 'price', 'createdAt'] as const
   355→const sort = ALLOWED_SORTS.find(s => s === req.nextUrl.searchParams.get('sort')) ?? 'createdAt'
   356→const products = await db.product.findMany({ orderBy: { [sort]: 'asc' } })
   357→```
   358→
   359→### 2.4 Webhook Security
   360→
   361→Webhooks (payment callbacks, etc.) are a prime attack surface. Three layers of defense:
   362→
   363→1. **HMAC signature verification** — verify the request actually came from the claimed sender.
   364→2. **Timestamp skew check** — reject requests older than 5 minutes (replay protection).
   365→3. **Nonce / idempotency key** — store the nonce in a DB table inside the transaction; reject
   366→   duplicates.
   367→
   368→```ts
   369→// Webhook verification
   370→const signature = req.headers.get('x-webhook-signature')  // hmac(rawBody + timestamp + nonce)
   371→const timestamp = req.headers.get('x-webhook-timestamp')
   372→const nonce = req.headers.get('x-webhook-nonce')
   373→
   374→// 1. Skew check (replay protection)
   375→const skew = Math.abs(Date.now() - Number(timestamp))
   376→if (skew > 5 * 60 * 1000) return NextResponse.json({ error: 'stale' }, { status: 401 })
   377→
   378→// 2. HMAC verify (constant-time comparison!)
   379→// In a Node-runtime route handler, use node:crypto (NOT crypto.subtle — see note below):
   380→import { createHmac, timingSafeEqual } from 'node:crypto'
   381→const expected = createHmac('sha256', WEBHOOK_SECRET)
   382→  .update(rawBody + timestamp + nonce)
   383→  .digest('hex')
   384→const sigBuf = Buffer.from(signature, 'hex')
   385→const expBuf = Buffer.from(expected, 'hex')
   386→if (sigBuf.length !== expBuf.length || !timingSafeEqual(sigBuf, expBuf)) {
   387→  return NextResponse.json({ error: 'invalid_sig' }, { status: 401 })
   388→}
   389→
   390→// 3. Nonce uniqueness (inside the Serializable transaction)
   391→await db.$transaction(async (tx) => {
   392→  await tx.idempotencyKey.create({ data: { key: nonce, expiresAt: new Date(Date.now() + 86400000) } })
   393→  // ... process webhook ...
   394→}, { isolationLevel: 'Serializable' })  // ← catches concurrent duplicate nonces
   395→```
   396→
   397→**Constant-time comparison**: Use `timingSafeEqual` from `node:crypto` on equal-length
   398→Buffers. **There is no `crypto.subtle.timingSafeEqual`** — that API does not exist in Web
   399→Crypto (a common AI-generated hallucination; it fails at runtime). On Edge runtime, use a
   400→custom constant-time XOR comparison. Never `===` for secret comparison — it leaks
   401→length/timing info.
   402→
   403→### 2.5 Rate Limiting
   404→
   405→Rate-limit ALL sensitive endpoints: login, contact form, checkout, password reset.
   406→
   407→```ts
   408→// src/lib/rate-limiter.ts
   409→const RATE_LIMIT = { windowMs: 60_000, max: 10 }  // 10 req/min/IP
   410→
   411→export async function rateLimit(ip: string, route: string) {
   412→  const key = `${route}:${ip}`
   413→  const entry = cache.get(key) ?? { count: 0, resetAt: Date.now() + RATE_LIMIT.windowMs }
   414→  if (Date.now() > entry.resetAt) {
   415→    entry.count = 0
   416→    entry.resetAt = Date.now() + RATE_LIMIT.windowMs
   417→  }
   418→  entry.count++
   419→  cache.set(key, entry)
   420→  if (entry.count > RATE_LIMIT.max) {
   421→    throw new RateLimitError(entry.resetAt)
   422→  }
   423→}
   424→```
   425→
   426→**IP extraction pitfall**: `X-Forwarded-For` can be spoofed. If behind a trusted proxy
   427→(Caddy, Cloudflare), take the LAST IP in the chain or use the proxy-specific header
   428→(`CF-Connecting-IP`, `X-Real-IP`). Never trust a client-supplied `X-Forwarded-For` directly.
   429→
   430→**Multi-instance warning**: The in-memory `cache` above is per-process. On serverless or
   431→multi-instance deployments, each instance keeps its own counter — the effective limit
   432→multiplies by the instance count. Back the limiter with shared storage (Redis / Upstash:
   433→atomic `INCR` + `EXPIRE`) whenever you scale beyond one instance.
   434→
   435→### 2.6 Secrets Management
   436→
   437→- ALL secrets live in `.env` (or environment variables in production). Never hardcoded.
   438→- The `NEXT_PUBLIC_` prefix makes a var available in the client bundle. **Only** use it for
   439→  truly public values (`NEXT_PUBLIC_SITE_URL`, `NEXT_PUBLIC_GA_ID`). Secrets like
   440→  `DATABASE_URL`, `PAYMENT_SECRET`, `JWT_SECRET` must NEVER have the `NEXT_PUBLIC_` prefix.
   441→- Validate secrets at startup — fail closed if missing or too short:
   442→
   443→```ts
   444→function getSecret(name: string): string {
   445→  const val = process.env[name]
   446→  if (!val) throw new Error(`Missing env var: ${name}`)
   447→  if (val.length < 32) throw new Error(`${name} must be at least 32 chars`)
   448→  return val
   449→}
   450→```
   451→
   452→### 2.7 IDOR (Insecure Direct Object Reference)
   453→
   454→Any endpoint that takes an ID (`/api/orders/[id]`, `/api/bookings/[id]`) MUST verify the
   455→requester owns that resource:
   456→
   457→```ts
   458→export async function GET(req: Request, { params }: { params: Promise<{ id: string }> }) {
   459→  const { id } = await params
   460→  const session = await requireAuth()
   461→  const order = await db.order.findFirst({
   462→    where: { id, userId: session.userId },  // ← scope to owner
   463→  })
   464→  if (!order) return NextResponse.json({ error: 'not_found' }, { status: 404 })
   465→}
   466→```
   467→
   468→Admin endpoints should scope by brand, not by user — but still verify the admin has access
   469→to that brand.
   470→
   471→### 2.8 Cookie Security
   472→
   473→Session cookies MUST have:
   474→- `httpOnly: true` — prevents JavaScript access (XSS protection)
   475→- `secure: true` — HTTPS only (in production)
   476→- `sameSite: 'lax'` — CSRF protection (or `'strict'` for maximum security)
   477→- `__Host-` prefix — binds the cookie to the host (no subdomain sharing)
   478→
   479→```ts
   480→// Must run inside a Server Action or Route Handler (set() is not allowed during renders)
   481→const store = await cookies()  // async since Next.js 15
   482→store.set('session', token, {
   483→  httpOnly: true,
   484→  secure: process.env.NODE_ENV === 'production',
   485→  sameSite: 'lax',
   486→  path: '/',
   487→  maxAge: 60 * 60 * 24,  // 24h — keep admin sessions short (policy: 24h max)
   488→})
   489→```

   491→### 2.9 Payment Integrity
   492→
   493→NEVER trust a client-supplied price. The server recomputes everything inside a Serializable
   494→transaction:
   495→
   496→```ts
   497→await db.$transaction(async (tx) => {
   498→  // 1. Fetch the product (with a fresh read inside the tx)
   499→  const product = await tx.product.findUniqueOrThrow({ where: { id } })
   500→  
   501→  // 2. Recompute days, totals
   502→  const days = computeDays(startDate, endDate)
   503→  const total = product.rentalPricePerDay * days * quantity
   504→  
   505→  // 3. Tolerance check (floating-point safety)
   506→  if (Math.abs(total - clientSuppliedTotal) > 0.001) {
   507→    throw new Error('PRICE_MISMATCH')
   508→  }
   509→  
   510→  // 4. Create the booking
   511→  await tx.booking.create({ data: { ... } })
   512→}, { isolationLevel: 'Serializable' })
   513→```

   515→### 2.10 Dev-Only Endpoints
   516→
   517→Mock/dev endpoints (test payment, debug routes) MUST be gated to non-production:
   518→
   519→```ts
   520→export async function POST() {
   521→  if (process.env.NODE_ENV === 'production') {
   522→    return NextResponse.json({ error: 'not_found' }, { status: 404 })
   523→  }
   524→  // ... dev-only logic ...
   525→}
   526→```
   527→
   528→### 2.11 Information Disclosure
   529→
   530→Error responses should NEVER leak:
   531→- Stack traces (use a generic message in production, log full trace server-side)
   532→- Internal file paths
   533→- DB schema / table names
   534→- Exact remaining stock counts (use generic "insufficient stock" messages)
   535→
   536→```ts
   537→// ❌ LEAKS INFO
   538→return NextResponse.json({ error: `Requested ${qty} but only ${available} left` }, { status: 409 })
   539→
   540→// ✅ SAFE
   541→return NextResponse.json({ error: 'out_of_stock', message: 'Requested quantity exceeds available stock' }, { status: 409 })
   542→```
   543→
   544→### 2.12 Security Headers
   545→
   546→Set baseline security headers centrally in `next.config.ts` — they then apply to every route
   547→(including API), with zero per-page effort:
   548→
   549→```ts
   550→// next.config.ts
   551→const securityHeaders = [
   552→  { key: 'X-Content-Type-Options', value: 'nosniff' },
   553→  { key: 'X-Frame-Options', value: 'DENY' },
   554→  { key: 'Referrer-Policy', value: 'strict-origin-when-cross-origin' },
   555→  { key: 'Permissions-Policy', value: 'camera=(), microphone=(), geolocation=()' },
   556→  { key: 'Strict-Transport-Security', value: 'max-age=63072000; includeSubDomains; preload' },
   557→  { key: 'Content-Security-Policy',
   558→    value: "default-src 'self'; img-src 'self' data: blob: https:; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline'; frame-ancestors 'none'" },
   559→]
   560→
   561→const nextConfig = {
   562→  async headers() {
   563→    return [{ source: '/:path*', headers: securityHeaders }]
   564→  },
   565→}
   566→
   567→export default nextConfig
   568→```
   569→
   570→- Tighten the CSP progressively toward nonces/hashes. `'unsafe-inline'` on `script-src` is a
   571→  last resort — acceptable at launch, not as the end state.
   572→- Add HSTS only after confirming HTTPS is fully working on the production domain — it pins
   573→  HTTPS permanently for returning visitors.
   574→- Verify with securityheaders.com after every deployment; a missing header after a config
   575→  rewrite is a classic silent regression.

   579→## 3. Database & Prisma Patterns
   580→
   581→### 3.1 Schema Design Principles
   582→
   583→**Money**: Use `Decimal` (not `Float`) for monetary values. Float has ~15 significant digits
   584→and accumulates rounding errors. If you MUST use Float (SQLite limitation), apply a
   585→`KWD_TOLERANCE = 0.001` check in every aggregation.
   586→
   587→```prisma
   588→model Product {
   589→  rentalPricePerDay Decimal @db.Decimal(10, 3)  // 3 decimal places for KWD
   590→}
   591→```
   592→
   593→**Status fields**: Use enums, not strings:
   594→
   595→```prisma
   596→enum BookingStatus {
   597→  PENDING
   598→  CONFIRMED
   599→  CANCELLED
   600→  COMPLETED
   601→  PAYMENT_FAILED
   602→}
   603→
   604→model Booking {
   605→  status BookingStatus @default(PENDING)
   606→}
   607→```
   608→
   609→**Timestamps**: Always include `createdAt` and `updatedAt` with defaults:
   610→
   611→```prisma
   612→model Booking {
   613→  createdAt DateTime @default(now())
   614→  updatedAt DateTime @updatedAt
   615→}
   616→```
   617→
   618→### 3.2 Indexes (Critical for Performance)
   619→
   620→Add compound indexes for every common query filter. Missing indexes cause full table scans
   621→that kill performance at scale.
   622→
   623→```prisma
   624→model Booking {
   625→  brand      Brand       @default(LUT)
   626→  status     BookingStatus @default(PENDING)
   627→  productId  String?
   628→  orderId    String?
   629→  
   630→  product    Product?    @relation(fields: [productId], references: [id], onDelete: SetNull)
   631→  
   632→  @@index([brand, status])           // admin dashboard filter
   633→  @@index([productId, status])       // availability queries
   634→  @@index([orderId])                // multi-item order grouping
   635→  @@index([brand, isActive, createdAt])  // storefront "newest in brand" sort
   636→}
   637→```
   638→
   639→**Rule of thumb**: For every `findMany({ where: { a, b } })`, there should be an
   640→`@@index([a, b])`. Foreign keys are NOT automatically indexed in SQLite — add them explicitly.
   641→
   642→### 3.3 Relations & onDelete
   643→
   644→Always declare `onDelete` behavior explicitly:
   645→
   646→| Setting | Use when |
   647→|---------|----------|
   648→| `Cascade` | Child can't exist without parent (e.g., OrderItem → Order) |
   649→| `SetNull` | Child should survive parent deletion (e.g., Booking → Product; booking history stays) |
   650→| `Restrict` | Prevent deletion if children exist (e.g., can't delete a Product with active bookings) |
   651→| `NoAction` | Default — DB decides (usually same as Restrict) |
   652→
   653→```prisma
   654→model Booking {
   655→  productId String?
   656→  product   Product? @relation(fields: [productId], references: [id], onDelete: SetNull)
   657→}
   658→```
   659→
   660→The FK field must be nullable (`String?`) for `SetNull` to work.
   661→
   662→### 3.4 Multi-Tenant Isolation
   663→
   664→If your app has multiple tenants (brands, organizations), every tenant-scoped model MUST
   665→have a `brand` (or `tenantId`) field. Every query MUST filter by it:
   666→
   667→```ts
   668→// ✅ Correct — always scope by brand
   669→export async function getProducts({ brand, ... }: { brand: Brand }) {
   670→  return db.product.findMany({ where: { brand, isActive: true } })
   671→}
   672→```
   673→
   674→Admin queries use `getAdminBrand()` to determine which brand the admin is managing:
   675→
   676→```ts
   677→export async function adminGetProducts(adminSession: Session) {
   678→  const brand = adminSession.brand  // from the session, not the URL
   679→  return db.product.findMany({ where: { brand } })
   680→}
   681→```
   682→
   683→**Pitfall**: A product lookup by ID alone (no brand filter) is acceptable IF the ID is a
   684→unguessable cuid. But availability checks should still scope by brand for defense-in-depth.
   685→
   686→### 3.5 Transactions & Concurrency
   687→
   688→Multi-step writes MUST be in a transaction. Booking/stock operations need `Serializable`
   689→isolation to prevent race conditions:
   690→
   691→```ts
   692→await db.$transaction(async (tx) => {
   693→  // 1. Check availability (fresh read inside tx)
   694→  const available = await checkStockAvailabilityInTx(tx, productId, startDate, endDate)
   695→  if (available < quantity) throw new Error('OUT_OF_STOCK')
   696→  
   697→  // 2. Create booking (within the same tx — next check sees this)
   698→  await tx.booking.create({ data: { ... } })
   699→}, { isolationLevel: 'Serializable' })
   700→```
   701→
   702→**Critical**: The stock check and the booking create MUST be in the same transaction. If they
   703→are in separate transactions (or sequential queries), two concurrent requests can both pass
   704→the check and both create bookings → **overbooking**.
   705→
   706→### 3.6 Booking Overlap Detection
   707→
   708→The hardest part of any rental system. The overlap condition is:
   709→
   710→```
   711→A booking overlaps B if: A.start < B.end AND A.end > B.start
   712→```
   713→
   714→For same-day rentals (where `start === end`), you MUST extend the effective end date by 24h
   715→on BOTH sides, or multi-day vs same-day comparisons break:
   716→
   717→```ts
   718→// ✅ Symmetric overlap detection
   719→function overlaps(requestStart: Date, requestEnd: Date, storedStart: Date, storedEnd: Date): boolean {
   720→  // Extend end dates to end-of-day for both request and stored
   721→  const requestEffectiveEnd = endOfDay(requestEnd)
   722→  const storedEffectiveEnd = endOfDay(storedEnd)
   723→  
   724→  return requestStart < storedEffectiveEnd && storedStart < requestEffectiveEnd
   725→}
   726→
   727→function endOfDay(d: Date): Date {
   728→  const copy = new Date(d)
   729→  copy.setUTCHours(23, 59, 59, 999)
   730→  return copy
   731→}
   732→```
   733→
   734→**The asymmetric bug — concrete example**: A customer tries to book a same-day rental on
   735→Aug 5 (`start = end = Aug 5 00:00`). Another user already holds a multi-day booking
   736→Aug 1–5, whose `end` is stored as `Aug 5 00:00` (NOT extended). The overlap check:
   737→`request.start (Aug 5 00:00) < stored.effectiveEnd (Aug 5 00:00)` → **false** → no overlap
   738→detected → double-booking on a day the existing booking actually owns. Extending BOTH
   739→sides to end-of-day catches it: `Aug 5 00:00 < Aug 5 23:59.999` → true. The rule:
   740→**always extend both sides** and use strict `<` — never extend only the request, never only
   741→the stored booking, and never mix `<` with `<=` across the two comparisons.
   742→
   743→### 3.7 PENDING Booking Expiry
   744→
   745→If your system has a PENDING state (booking created, awaiting payment), PENDING bookings
   746→lock stock indefinitely unless they expire. This is a DoS vector — an attacker can spam
   747→PENDING bookings to exhaust all stock.
   748→
   749→**Fix**: Filter out PENDING bookings older than a TTL (e.g., 30 minutes) in availability
   750→queries:
   751→
   752→```ts
   753→const PENDING_BOOKING_TTL_MS = 30 * 60 * 1000
   754→
   755→export async function checkStockAvailability(productId: string, start: Date, end: Date) {
   756→  const activeBookings = await db.booking.findMany({
   757→    where: {
   758→      productId,
   759→      OR: [
   760→        { status: { in: ['CONFIRMED', 'COMPLETED'] } },
   761→        { status: 'PENDING', createdAt: { gte: new Date(Date.now() - PENDING_BOOKING_TTL_MS) } },
   762→      ],
   763→      // overlap condition...
   764→    },
   765→  })
   766→}
   767→```
   768→
   769→This is "lazy GC" — no cron job needed. Stale PENDING bookings are simply ignored.
   770→
   771→### 3.8 Prisma Error Handling
   772→
   773→Catch specific Prisma error codes and return user-friendly messages:
   774→
   775→```ts
   776→import { Prisma } from '@prisma/client'
   777→
   778→try {
   779→  await db.product.create({ data: { ... } })
   780→} catch (e) {
   781→  if (e instanceof Prisma.PrismaClientKnownRequestError) {
   782→    if (e.code === 'P2002') {
   783→      // Unique constraint violation
   784→      return { error: 'slug_exists' }
   785→    }
   786→    if (e.code === 'P2025') {
   787→      // Record not found
   788→      return { error: 'not_found' }
   789→    }
   790→    if (e.code === 'P2034') {
   791→      // Transaction conflict (race condition)
   792→      return { error: 'conflict_retry' }
   793→    }
   794→  }
   795→  throw e  // re-throw unknown errors
   796→}
   797→```
   798→
   799→**TOCTOU fix**: The `findFirst` duplicate-check + `create` pattern is not atomic. Even if
   800→you pre-check, a concurrent request can create the same record between check and create.
   801→The P2002 catch is the real safety net — always have it.
   802→
   803→### 3.9 Multi-Item Orders
   804→
   805→If a cart can have multiple items, ALL bookings created in one checkout MUST be grouped
   806→under a shared `orderId`. Any status change (confirm, cancel) applies to ALL bookings in
   807→the order:
   808→
   809→```ts
   810→// Generate one orderId per checkout
   811→const orderId = `ORD-${Date.now()}-${randomSuffix}`
   812→
   813→await db.$transaction(async (tx) => {
   814→  for (const item of items) {
   815→    await tx.booking.create({
   816→      data: { ...item, orderId },  // ← shared orderId
   817→    })
   818→  }
   819→})
   820→
   821→// Payment webhook confirms ALL bookings in the order
   822→await db.booking.updateMany({
   823→  where: { orderId },
   824→  data: { status: 'CONFIRMED' },
   825→})
   826→```
   827→
   828→**Critical pitfall**: If you return `bookings[0].id` as the orderId and the webhook only
   829→confirms that single booking, the other items stay PENDING forever (and silently release
   830→stock after the TTL).
   831→
   832→### 3.10 Soft Deletes vs Hard Deletes
   833→
   834→Pick ONE pattern and apply it consistently:
   835→
   836→| Pattern | When | Example |
   837→|---------|------|---------|
   838→| Soft delete (`isActive: boolean`) | When historical data matters (orders, bookings, products) | `where: { isActive: true }` on every read |
   839→| Hard delete (`delete()`) | When data is truly disposable (drafts, temp tokens) | Categories if no order references them |
   840→
   841→**Inconsistency warning**: If Product uses soft-delete but Category uses hard-delete, you'll
   842→have orphaned products when a category is deleted. Either cascade-soft-delete or use
   843→`onDelete: Restrict` to prevent deletion with active children.
   844→
   845→### 3.11 Date Normalization
   846→
   847→Dates from the client are timezone-dependent. A user in UTC+3 selecting "Aug 1" sends
   848→`Aug 1 00:00 +03:00` = `Jul 31 21:00 UTC`. Two users in different timezones booking the
   849→"same" calendar date produce non-overlapping UTC ranges → phantom availability or
   850→double-booking.
   851→
   852→**Fix**: Normalize all dates to midnight UTC server-side:
   853→
   854→```ts
   855→// Client sends YYYY-MM-DD; server normalizes
   856→function normalizeToUTCMidnight(dateString: string): Date {
   857→  return new Date(`${dateString}T00:00:00.000Z`)
   858→}
   859→```
   860→
   861→If the client sends full ISO timestamps, extract the date and re-normalize:
   862→
   863→```ts
   864→const dateOnly = new Date(clientDate).toISOString().split('T')[0]
   865→const normalized = new Date(`${dateOnly}T00:00:00.000Z`)
   866→```
   867→
   868→### 3.12 DB Path Consistency (SQLite)
   869→
   870→SQLite's `file:./path` is RELATIVE to the schema file location (`prisma/schema.prisma`).
   871→`file:./db/app.db` from the schema resolves to `prisma/db/app.db`. But if you set
   872→`DATABASE_URL=file:./prisma/db/app.db` in package.json scripts, Prisma resolves it relative
   873→to the schema → `prisma/prisma/db/app.db` — a different file!
   874→
   875→**Rule**: Use ONE consistent path everywhere:
   876→- `.env`: `DATABASE_URL="file:./db/app.db"` (relative to schema)
   877→- `package.json` scripts: `DATABASE_URL=file:./db/app.db` (same)
   878→- Or use an ABSOLUTE path in `.env`: `DATABASE_URL="file:/abs/path/to/app.db"`
   879→
   880→Verify with: `find . -name "*.db" -not -path "*/node_modules/*"` — there should be exactly ONE.
   881→

   884→## 4. TypeScript & Code Quality
   885→
   886→### 4.1 Strict Mode (Non-Negotiable)
   887→
   888→`tsconfig.json`:
   889→```json
   890→{
   891→  "compilerOptions": {
   892→    "strict": true,
   893→    "noUncheckedIndexedAccess": true,
   894→    "noImplicitOverride": true,
   895→    "exactOptionalPropertyTypes": true
   896→  }
   897→}
   898→```
   899→
   900→### 4.2 The `any` Taxonomy
   901→
   902→| Form | Severity | When OK |
   903→|------|----------|---------|
   904→| `: any` | Avoid | Never in production code |
   905→| `as any` | Avoid | Never — fix the type instead |
   906→| `unknown` | OK | When you genuinely don't know the shape (parse first) |
   907→| `Record<string, unknown>` | OK | Generic JSON payloads |
   908→
   909→Replace `any` with proper types. If you can't, use `unknown` and narrow:
   910→
   911→```ts
   912→// ❌
   913→function parse(data: any) { return data.users.map((u: any) => u.name) }
   914→
   915→// ✅
   916→function parse(data: unknown): string[] {
   917→  const obj = data as { users?: Array<{ name?: unknown }> }
   918→  if (!obj.users || !Array.isArray(obj.users)) return []
   919→  return obj.users.map(u => (typeof u.name === 'string' ? u.name : '')).filter(Boolean)
   920→}
   921→```
   922→
   923→### 4.3 Non-Null Assertions (`!`)
   924→
   925→`value!` tells TypeScript "trust me, this isn't null." It's a runtime crash waiting to
   926→happen. Replace with explicit checks:
   927→
   928→```ts
   929→// ❌ Crash if canvas is null
   930→const ctx = canvas.getContext('2d')!
   931→
   932→// ✅ Safe
   933→const ctx = canvas.getContext('2d')
   934→if (!ctx) throw new Error('Canvas 2D context unavailable')
   935→```
   936→
   937→### 4.4 Error Handling
   938→
   939→Never swallow errors silently. The empty catch `catch (e) {}` is a bug factory — when
   940→something breaks, you'll have no idea why.
   941→
   942→```ts
   943→// ❌ Silent failure
   944→try { await action() } catch (e) {}
   945→
   946→// ❌ Logs but doesn't surface
   947→try { await action() } catch (e) { console.error(e) }
   948→
   949→// ✅ Log + handle
   950→try {
   951→  await action()
   952→} catch (e) {
   953→  console.error('[Context] action failed:', e)
   954→  showToast('error', t('errors.generic'))
   955→} finally {
   956→  setSubmitting(false)  // ← ALWAYS reset loading state in finally
   957→}
   958→```
   959→
   960→**Loading state rule**: If you set `setSubmitting(true)` before an await, you MUST reset it
   961→in a `finally` block — not in the `try` (which skips on error) and not only in `catch`
   962→(which leaves it stuck on success-with-no-throw paths).
   963→
   964→### 4.5 React Anti-Patterns
   965→
   966→| Anti-pattern | Fix |
   967→|--------------|-----|
   968→| Missing `key` in `.map()` | Use a stable ID (not array index) |
   969→| `useEffect` with missing deps | Either add the dep or wrap in `useCallback`/`useMemo` |
   970→| `useEffect` for derived state | Compute inline: `const total = price * qty` |
   971→| `useState` for computed value | Use `useMemo` or just compute inline |
   972→| `setInterval`/`setTimeout` without cleanup | Return a cleanup function from `useEffect` |
   973→| Event listener without removal | `useEffect(() => { el.addEventListener(...); return () => el.removeEventListener(...) }, [])` |
   974→| `useRef` for derived data | Use `useMemo` |
   975→| Reading `window`/`document` in render | Move to `useEffect` |
   976→
   977→### 4.6 Dynamic i18n Keys
   978→
   979→When building i18n keys dynamically (e.g., `t(\`status.${booking.status}\`)`), you risk a
   980→`MISSING_MESSAGE` error if the status value has no key. Always guard:
   981→
   982→```ts
   983→const statusKey = `admin.bookings.filterStatus.${booking.status}`
   984→const statusLabel = t.has(statusKey) ? t(statusKey) : booking.status
   985→```
   986→
   987→### 4.7 Dead Code Prevention
   988→
   989→- Exported but never imported → delete (verify with Grep first).
   990→- Typed props that are silently ignored → remove from the interface AND all call sites.
   991→- Commented-out code blocks → delete (use git history, not comments).
   992→- Unused imports → ESLint catches these; run `bun run lint` regularly.
   993→
   994→### 4.8 Brand-Aware Routing
   995→
   996→In a multi-brand app, shared components (ProductCard, CartButton, Breadcrumbs) must build
   997→URLs based on the active brand. Centralize this in ONE helper:
   998→
   999→```ts
  1000→// src/lib/brand.ts
  1001→export function resolveBrandFromPath(pathname: string): 'lut' | 'lalounge' | 'birthday' {
  1002→  if (pathname.startsWith('/la-lounge')) return 'lalounge'
  1003→  if (pathname.startsWith('/your-birthday')) return 'birthday'
  1004→  return 'lut'
  1005→}
  1006→
  1007→export function getProductsBasePath(brand: Brand): string {
  1008→  switch (brand) {
  1009→    case 'birthday': return '/your-birthday/products'
  1010→    case 'lalounge': return '/products'  // La Lounge shares the LUT storefront
  1011→    default: return '/products'
  1012→  }
  1013→}
  1014→
  1015→export function getCartHref(brand: Brand): string {
  1016→  return brand === 'birthday' ? '/your-birthday/cart' : '/cart'
  1017→}
  1018→```
  1019→
  1020→**Pitfall**: If `ProductCard` hardcodes `href={\`/products/${slug}\`}`, it 404s on the
  1021→Your Birthday storefront (where slugs live at `/your-birthday/products/[slug]`). Use the
  1022→helper everywhere.
  1023→
  1024→### 4.9 Component Size Guidelines
  1025→
  1026→- **Under 100 lines**: Ideal.
  1027→- **100–300 lines**: Acceptable if cohesive.
  1028→- **300–500 lines**: Refactor — extract sub-components.
  1029→- **Over 500 lines**: Code smell. Split immediately.
  1030→
  1031→### 4.10 Brand Color Consistency
  1032→
  1033→Declare brand colors ONCE in a constants file. Never hardcode hex values in components:
  1034→
  1035→```ts
  1036→// src/lib/brand-colors.ts
  1037→export const BRAND_COLORS = {
  1038→  LUT: '#8B6B3D',
  1039→  LA_LOUNGE: '#E6007E',
  1040→  YOUR_BIRTHDAY: '#FFCC00',
  1041→} as const
  1042→```
  1043→
  1044→If you find `#F5B914` (an old color) anywhere in components, it's a stale reference. Grep
  1045→for all hex values and consolidate. Components should use CSS variables (`bg-primary`,
  1046→`text-foreground`) set via `data-brand` on `<html>`, not hardcoded hexes.
  1047→
  1048→### 4.11 Structured Logging
  1049→
  1050→`console.log('booking done')` is unsearchable at scale. Log **events** as JSON with stable
  1051→fields (server-side only — never in client components):
  1052→
  1053→```ts
  1054→console.info(JSON.stringify({
  1055→  level: 'info',
  1056→  event: 'booking.created',   // events, not sentences
  1057→  orderId,
  1058→  brand,
  1059→  correlationId,              // per-request UUID, attached to every log of that request
  1060→}))
  1061→```
  1062→
  1063→- A `correlationId` generated per request lets you follow one request across proxy → route →
  1064→  webhook logs — this is what turns logs from noise into a timeline.
  1065→- Never log secrets, session tokens, or customer PII. Log **IDs**, not payloads.
  1066→- In production, pipe these into Sentry / Railway logs and alert on `level: 'error'` spikes
  1067→  (see the Assistant Agent manual, Ch. 11 for the monitoring cadence).

  1071→## 5. Internationalization (i18n)
  1072→
  1073→### 5.1 Key Parity
  1074→
  1075→EN and AR JSON files MUST have exactly the same keys. Any mismatch causes a `MISSING_MESSAGE`
  1076→error in one language. Verify with a diff script:
  1077→
  1078→```js
  1079→// scripts/check-i18n-parity.js
  1080→const fs = require('fs')
  1081→function flat(o, p = '') {
  1082→  return Object.entries(o).flatMap(([k, v]) =>
  1083→    typeof v === 'object' && v !== null ? flat(v, p + k + '.') : [p + k]
  1084→  )
  1085→}
  1086→const en = flat(JSON.parse(fs.readFileSync('messages/en.json', 'utf8'))).sort()
  1087→const ar = flat(JSON.parse(fs.readFileSync('messages/ar.json', 'utf8'))).sort()
  1088→const enOnly = en.filter(k => !ar.includes(k))
  1089→const arOnly = ar.filter(k => !en.includes(k))
  1090→if (enOnly.length || arOnly.length) {
  1091→  console.error('PARITY FAIL:', { enOnly, arOnly })
  1092→  process.exit(1)
  1093→}
  1094→console.log(`Parity OK: ${en.length} keys`)
  1095→```
  1096→
  1097→Run this in CI. It catches missing translations immediately.
  1098→
  1099→### 5.2 Snake_case vs camelCase
  1100→
  1101→Pick ONE convention for i18n keys. Mixing them creates "orphaned duplicates":
  1102→
  1103→```json
  1104→// ❌ Both exist — which does the code use?
  1105→{
  1106→  "errors": {
  1107→    "out_of_stock": "Out of stock",
  1108→    "outOfStock": "Out of stock"
  1109→  }
  1110→}
  1111→```
  1112→
  1113→**Rule**: Use camelCase consistently (`outOfStock`, `invalidInput`). If you see snake_case
  1114→duplicates, verify they're not referenced (Grep), then delete them.
  1115→
  1116→### 5.3 ICU Placeholders
  1117→
  1118→Use ICU format for interpolation — it's consistent across locales:
  1119→
  1120→```json
  1121→{
  1122→  "cart": {
  1123→    "itemCount": "{count, plural, =0 {Empty} =1 {1 item} other {# items}}",
  1124→    "welcome": "Welcome, {name}"
  1125→  }
  1126→}
  1127→```
  1128→
  1129→```tsx
  1130→t('cart.itemCount', { count: items.length })
  1131→t('cart.welcome', { name: user.name })
  1132→```
  1133→
  1134→**Pitfall**: Plural forms differ between languages. Arabic has 6 plural forms (zero, one,
  1135→two, few, many, other). next-intl handles this if you use the `plural` format — but verify
  1136→AR translations include all forms.
  1137→
  1138→### 5.4 Server vs Client Translation Hooks
  1139→
  1140→- `useTranslations()` — CLIENT hook only. Crashes in server components.
  1141→- `getTranslations()` — SERVER async function. Use in server components, layouts, pages.
  1142→
  1143→```tsx
  1144→// ✅ Server component
  1145→export default async function Page() {
  1146→  const t = await getTranslations()
  1147→  return <h1>{t('home.title')}</h1>
  1148→}
  1149→
  1150→// ✅ Client component
  1151→'use client'
  1152→export function Client() {
  1153→  const t = useTranslations()
  1154→  return <h1>{t('home.title')}</h1>
  1155→}
  1156→```
  1157→
  1158→**Pitfall**: `not-found.tsx` and `error.tsx` may render before the i18n provider mounts
  1159→(e.g., invalid locale). Use `getTranslations()` (server) with a locale fallback, not
  1160→`useTranslations()` (client).
  1161→
  1162→### 5.5 RTL Support
  1163→
  1164→- Use logical properties (`ms-4` not `ml-4`, `ps-4` not `pl-4`, `start-0` not `left-0`).
  1165→- Tailwind 4 supports `ms-`/`me-`/`ps-`/`pe-`/`start-`/`end-` which flip automatically in RTL.
  1166→- Set `<html dir="rtl">` for Arabic (next-intl does this via the locale).
  1167→- Test EVERY page in RTL — icons, padding, flex direction all need verification.
  1168→
  1169→### 5.6 Brand Name Consistency
  1170→
  1171→Brand names must be spelled identically in both languages:
  1172→
  1173→```json
  1174→// en.json
  1175→{ "brandSelector": { "lalounge": { "name": "La Lounge" } } }
  1176→
  1177→// ar.json
  1178→{ "brandSelector": { "lalounge": { "name": "لا لاونج" } } }
  1179→```
  1180→
  1181→Don't mix "La Lounge" and "LaLounge" and "la lounge" — pick one per language.

  1185→## 6. Business Logic: Booking, Cart, Checkout, Payment
  1186→
  1187→### 6.1 The Complete Booking Flow
  1188→
  1189→```
  1190→Cart (client)
  1191→  → Checkout page (client, validates cart)
  1192→    → POST /api/orders (server, Serializable tx)
  1193→      → Check availability per item (interleaved with create)
  1194→      → Create Booking per item (all under one orderId)
  1195→      → Return orderId to client
  1196→    → Redirect to /checkout/payment?order=ORD-...
  1197→      → Payment view fetches ALL bookings by orderId, sums total
  1198→      → User confirms
  1199→    → Payment webhook (server, HMAC verified)
  1200→      → Find ALL bookings by orderId
  1201→      → Validate state machine (all PENDING)
  1202→      → Update ALL to CONFIRMED (in transaction)
  1203→    → Redirect to /checkout/success
  1204→```
  1205→
  1206→### 6.2 Stock Check + Create MUST Be Interleaved
  1207→
  1208→The #1 overbooking bug: checking all items' availability FIRST, then creating all bookings.
  1209→Two items for the same product both pass the check, then both get created.
  1210→
  1211→```ts
  1212→// ❌ OVERBOOKING BUG
  1213→for (const item of items) {
  1214→  const available = await checkAvailability(item)  // all checks first
  1215→  if (available < item.quantity) throw error
  1216→}
  1217→for (const item of items) {
  1218→  await tx.booking.create({ data: item })  // all creates after
  1219→}
  1220→
  1221→// ✅ CORRECT — interleaved
  1222→for (const item of items) {
  1223→  const available = await checkStockAvailabilityInTx(tx, item.productId, item.startDate, item.endDate)
  1224→  if (available < item.quantity) throw new Error('OUT_OF_STOCK')
  1225→  await tx.booking.create({ data: { ...item, orderId } })  // next iteration sees this
  1226→}
  1227→```
  1228→
  1229→The second item's check runs AFTER the first booking is created (within the same
  1230→Serializable transaction), so it sees the reduced stock.
  1231→
  1232→### 6.3 Cart Validation at Checkout
  1233→
  1234→The cart is client-side (localStorage). It can be stale — a product may have been
  1235→deactivated, had its price changed, or gone out of stock. Validate against the DB at
  1236→checkout:
  1237→
  1238→```ts
  1239→// POST /api/orders
  1240→const products = await db.product.findMany({
  1241→  where: { id: { in: items.map(i => i.productId) }, isActive: true },
  1242→})
  1243→if (products.length !== items.length) {
  1244→  return NextResponse.json({ error: 'invalid_products' }, { status: 400 })
  1245→}
  1246→// Recompute price from DB (never trust client price)
  1247→```
  1248→
  1249→### 6.4 Payment State Machine
  1250→
  1251→Define valid status transitions and enforce them:
  1252→
  1253→```ts
  1254→const VALID_TRANSITIONS: Record<BookingStatus, BookingStatus[]> = {
  1255→  PENDING: ['CONFIRMED', 'CANCELLED', 'PAYMENT_FAILED'],
  1256→  CONFIRMED: ['COMPLETED', 'CANCELLED'],
  1257→  CANCELLED: [],  // terminal
  1258→  COMPLETED: [],  // terminal
  1259→  PAYMENT_FAILED: ['CONFIRMED', 'CANCELLED'],  // retry allowed
  1260→}
  1261→
  1262→function canTransition(from: BookingStatus, to: BookingStatus): boolean {
  1263→  return VALID_TRANSITIONS[from]?.includes(to) ?? false
  1264→}
  1265→```
  1266→
  1267→In the webhook, validate the transition BEFORE updating:
  1268→
  1269→```ts
  1270→const booking = await tx.booking.findFirstOrThrow({ where: { id } })
  1271→if (!canTransition(booking.status, 'CONFIRMED')) {
  1272→  throw new Error(`Invalid transition: ${booking.status} → CONFIRMED`)
  1273→}
  1274→await tx.booking.update({ where: { id }, data: { status: 'CONFIRMED' } })
  1275→```
  1276→
  1277→### 6.5 Webhook Idempotency
  1278→
  1279→If the payment gateway retries the webhook (which they do), you must not double-process.
  1280→Use an `IdempotencyKey` table:
  1281→
  1282→```prisma
  1283→model IdempotencyKey {
  1284→  key       String   @id
  1285→  expiresAt DateTime
  1286→  createdAt DateTime @default(now())
  1287→  
  1288→  @@index([expiresAt])
  1289→}
  1290→```
  1291→
  1292→```ts
  1293→await db.$transaction(async (tx) => {
  1294→  // This throws P2002 if the key already exists (duplicate webhook)
  1295→  await tx.idempotencyKey.create({
  1296→    data: { key: webhookNonce, expiresAt: new Date(Date.now() + 86400000) },
  1297→  })
  1298→  // ... process the webhook ...
  1299→}, { isolationLevel: 'Serializable' })
  1300→```
  1301→
  1302→**GC note**: Add a periodic cleanup for expired keys, or filter by `expiresAt > now()` on
  1303→insert (lazy GC).
  1304→
  1305→### 6.6 Multi-Brand Cart Isolation
  1306→
  1307→If brands have separate storefronts, the cart should be brand-scoped. Either:
  1308→- Separate cart per brand (cart key includes brand: `lut-cart`, `birthday-cart`)
  1309→- Reject cross-brand items at add-to-cart
  1310→
  1311→```ts
  1312→// Adding to cart
  1313→const currentBrand = resolveBrandFromPath(pathname)
  1314→const cart = getCart(currentBrand)
  1315→if (cart.items.length && cart.items[0].brand !== product.brand) {
  1316→  // Cross-brand — either reject or clear the cart first
  1317→  showToast('error', t('cart.crossBrand'))
  1318→  return
  1319→}
  1320→```

  1324→## 7. Accessibility (a11y) & UX
  1325→
  1326→### 7.1 WCAG 2.1 AA Checklist
  1327→
  1328→For EVERY interactive element:
  1329→- [ ] Semantic HTML (`<button>` not `<div onClick>`, `<a href>` not `<span onClick>`)
  1330→- [ ] Keyboard reachable (Tab key moves focus)
  1331→- [ ] Visible focus indicator (`focus-visible:ring-2`)
  1332→- [ ] 44px minimum touch target (mobile)
  1333→- [ ] `aria-label` on icon-only buttons (cart, search, close, menu)
  1334→- [ ] `alt` text on all images (empty `alt=""` for decorative)
  1335→
  1336→For EVERY form:
  1337→- [ ] `<label>` associated with each input (or `aria-label`)
  1338→- [ ] Required fields marked (`aria-required` or visual `*`)
  1339→- [ ] Inline validation with `aria-invalid` and `aria-describedby`
  1340→- [ ] Error messages in `role="alert"` with red color (not brand color)
  1341→
  1342→For EVERY dynamic content:
  1343→- [ ] Loading states: `role="status"` + `aria-live="polite"` + `sr-only` text
  1344→- [ ] Error toasts: `role="alert"` + `aria-live="assertive"`
  1345→- [ ] Modals: focus trap, `role="dialog"`, `aria-modal="true"`, ESC to close
  1346→- [ ] Success confirmations: move focus to the message, don't auto-close too fast
  1347→
  1348→### 7.2 Color Contrast
  1349→
  1350→WCAG AA requires:
  1351→- Normal text: 4.5:1 contrast ratio
  1352→- Large text (18pt+ or 14pt bold): 3:1
  1353→- UI components: 3:1
  1354→
  1355→Avoid low-opacity text on dark backgrounds:
  1356→```tsx
  1357→// ❌ Fails AA (text-paper/30 = ~2:1)
  1358→<p className="text-paper/30">Crafted in Kuwait</p>
  1359→
  1360→// ✅ Passes AA (text-paper/60 = ~5:1)
  1361→<p className="text-paper/60">Crafted in Kuwait</p>
  1362→```
  1363→
  1364→### 7.3 Brand-Aware Links in Shared Components
  1365→
  1366→Footer, navbar, breadcrumbs — all shared components must build links based on the active
  1367→brand. A footer that hardcodes `/products` breaks on the Your Birthday storefront.
  1368→
  1369→```tsx
  1370→// ✅ Brand-aware footer links
  1371→function Footer() {
  1372→  const pathname = usePathname()
  1373→  const brand = resolveBrandFromPath(pathname)
  1374→  const productsHref = getProductsBasePath(brand)
  1375→  const contactHref = getContactHref(brand)
  1376→  
  1377→  return (
  1378→    <nav>
  1379→      <Link href={productsHref}>Products</Link>
  1380→      <Link href={contactHref}>Contact</Link>
  1381→    </nav>
  1382→  )
  1383→}
  1384→```
  1385→
  1386→### 7.4 3D Background Fallbacks
  1387→
  1388→3D WebGL backgrounds early-return on `prefers-reduced-motion: reduce`, no WebGL, or
  1389→low-end devices. Without a fallback, the page background is white and hero text (often
  1390→light-colored) becomes invisible.
  1391→
  1392→**Fix**: Add a dark gradient fallback on the hero wrapper:
  1393→
  1394→```css
  1395→/* globals.css */
  1396→.brand-hero-fallback {
  1397→  background: linear-gradient(135deg, #1a1a1a 0%, #0a0a0a 100%);
  1398→}
  1399→[data-brand="lalounge"] .brand-hero-fallback {
  1400→  background: linear-gradient(135deg, #150912 0%, #0a0408 100%);
  1401→}
  1402→[data-brand="birthday"] .brand-hero-fallback {
  1403→  background: linear-gradient(135deg, #2a1f0a 0%, #150f05 100%);
  1404→}
  1405→```
  1406→
  1407→```tsx
  1408→// The 3D canvas renders on top (z-0); the fallback shows when 3D is disabled
  1409→<div className="brand-hero-fallback min-h-screen">
  1410→  <Heavy3D />  {/* position: fixed; z-0; renders null if disabled */}
  1411→  <div className="relative z-10">{/* hero text */}</div>
  1412→</div>
  1413→```
  1414→
  1415→Also add a `loading` fallback to the `dynamic()` import (not `null`):
  1416→
  1417→```tsx
  1418→const Heavy3D = dynamic(() => import('./heavy-3d'), {
  1419→  ssr: false,
  1420→  loading: () => <div className="fixed inset-0 -z-10 bg-background" />,
  1421→})
  1422→```
  1423→
  1424→### 7.5 Focus Management on State Change
  1425→
  1426→When a modal/dialog shows a success state, move focus to it. Screen reader users won't
  1427→know the state changed otherwise.
  1428→
  1429→```tsx
  1430→const successRef = useRef<HTMLDivElement>(null)
  1431→const [success, setSuccess] = useState(false)
  1432→
  1433→useEffect(() => {
  1434→  if (success && successRef.current) {
  1435→    successRef.current.focus()
  1436→  }
  1437→}, [success])
  1438→
  1439→return (
  1440→  <div ref={successRef} role="status" aria-live="assertive" tabIndex={-1}>
  1441→    {success ? 'Booking confirmed!' : 'Processing...'}
  1442→  </div>
  1443→)
  1444→```
  1445→
  1446→### 7.6 Hydration Flash Prevention
  1447→
  1448→Values computed client-side (like `total.toFixed(3)`) flash `0.000` before hydration. Guard
  1449→them:
  1450→
  1451→```tsx
  1452→const [mounted, setMounted] = useState(false)
  1453→useEffect(() => setMounted(true), [])
  1454→
  1455→const displayTotal = mounted ? total.toFixed(3) : '—'
  1456→```
  1457→
  1458→### 7.7 Sticky Footer
  1459→
  1460→```tsx
  1461→<body className="min-h-screen flex flex-col">
  1462→  <Navbar />
  1463→  <main className="flex-1">{children}</main>
  1464→  <Footer className="mt-auto" />

  1472→## 8. Performance & SEO
  1473→
  1474→### 8.1 Image Optimization
  1475→
  1476→Always use `next/image` (not raw `<img>`). It optimizes format (WebP/AVIF), size, and lazy-
  1477→loads. Every image needs `alt` and either `width`/`height` or `fill` + `sizes`.
  1478→
  1479→```tsx
  1480→import Image from 'next/image'
  1481→
  1482→// ✅ Fixed dimensions
  1483→<Image src={img} alt={product.name} width={400} height={400} />
  1484→
  1485→// ✅ Fill (needs sized parent + sizes)
  1486→<div className="relative aspect-square">
  1487→  <Image src={img} alt={name} fill sizes="(max-width: 768px) 100vw, 33vw" />
  1488→</div>
  1489→```
  1490→
  1491→### 8.2 Font Optimization
  1492→
  1493→Use `next/font` (not raw `<link>` to Google Fonts). It self-hosts, preloads, and avoids
  1494→render-blocking:
  1495→
  1496→```tsx
  1497→import { Inter, Cairo } from 'next/font/google'
  1498→
  1499→const inter = Inter({ subsets: ['latin'], variable: '--font-inter' })
  1500→const cairo = Cairo({ subsets: ['arabic'], variable: '--font-cairo' })
  1501→
  1502→export default function RootLayout({ children }) {
  1503→  return (
  1504→    <html className={`${inter.variable} ${cairo.variable}`}>
  1505→      <body>{children}</body>
  1506→    </html>
  1507→  )
  1508→}
  1509→```
  1510→
  1511→For non-default fonts (e.g., a brand-specific font only used on some pages), set
  1512→`preload: false` to avoid preloading unused fonts.
  1513→
  1514→### 8.3 Bundle Size
  1515→
  1516→- Three.js, Chart.js, and any >50KB library: `dynamic(() => import(...), { ssr: false })`
  1517→- Don't import entire icon libraries: `import { Menu } from 'lucide-react'` (tree-shaken), not
  1518→  `import * as Icons from 'lucide-react'`.
  1519→- Check for `'use client'` components importing server-only modules.
  1520→
  1521→### 8.4 Caching Strategy
  1522→
  1523→- Static pages: `generateStaticParams` + `dynamicParams = false` (pre-rendered at build)
  1524→- ISR: `export const revalidate = 3600` (revalidate every hour)
  1525→- Dynamic data: `dynamic = 'force-dynamic'` or no cache directive
  1526→- Per-request: `fetch(url, { cache: 'no-store' })` or `fetch(url, { next: { revalidate: 60 } })`
  1527→
  1528→### 8.5 generateStaticParams
  1529→
  1530→Every dynamic route (`[slug]`, `[id]`) should export `generateStaticParams` to pre-render
  1531→known pages at build time:
  1532→
  1533→```tsx
  1534→export async function generateStaticParams() {
  1535→  const products = await db.product.findMany({
  1536→    where: { isActive: true },
  1537→    select: { slug: true },
  1538→  })
  1539→  return products.map(p => ({ slug: p.slug }))
  1540→}
  1541→
  1542→export const dynamicParams = false  // 404 for unknown slugs
  1543→```
  1544→
  1545→### 8.6 Metadata
  1546→
  1547→Every page should export `metadata` or `generateMetadata`. Use a centralized `buildMetadata`
  1548→helper:
  1549→
  1550→```ts
  1551→// src/lib/seo.ts
  1552→export function buildMetadata({ locale, path, title, description }: MetadataInput): Metadata {
  1553→  const baseUrl = process.env.NEXT_PUBLIC_SITE_URL || 'http://localhost:3000'
  1554→  return {
  1555→    title,
  1556→    description,
  1557→    alternates: {
  1558→      canonical: `${baseUrl}/${locale}${path}`,
  1559→      languages: { en: `${baseUrl}/en${path}`, ar: `${baseUrl}/ar${path}` },
  1560→    },
  1561→    openGraph: { title, description, url: `${baseUrl}/${locale}${path}` },
  1562→  }
  1563→}
  1564→```
  1565→
  1566→**Never hardcode the site URL** — always use `process.env.NEXT_PUBLIC_SITE_URL`. Hardcoded
  1567→URLs leak the wrong domain in preview/staging.
  1568→
  1569→### 8.7 Sitemap
  1570→
  1571→`src/app/sitemap.ts` should list ALL indexable URLs (200-OK only, no redirects):
  1572→
  1573→```ts
  1574→export default async function sitemap(): Promise<MetadataRoute.Sitemap> {
  1575→  const baseUrl = process.env.NEXT_PUBLIC_SITE_URL || 'http://localhost:3000'
  1576→  
  1577→  // Static pages
  1578→  const staticEntries = [...].map(path => ({
  1579→    url: `${baseUrl}/en${path}`,
  1580→    alternates: { languages: { en: `${baseUrl}/en${path}`, ar: `${baseUrl}/ar${path}` } },
  1581→    priority: 0.8,
  1582→  }))
  1583→  
  1584→  // Dynamic product pages (ALL brands with storefronts)
  1585→  const products = await db.product.findMany({
  1586→    where: { isActive: true, brand: { in: ['LUT', 'YOUR_BIRTHDAY'] } },
  1587→    select: { slug: true, brand: true, updatedAt: true },
  1588→  })
  1589→  
  1590→  const productEntries = products.map(p => ({
  1591→    url: `${baseUrl}/en${p.brand === 'YOUR_BIRTHDAY' ? '/your-birthday' : ''}/products/${p.slug}`,
  1592→    lastModified: p.updatedAt,
  1593→    alternates: { languages: { en: '...', ar: '...' } },
  1594→    priority: 0.8,
  1595→  }))
  1596→  
  1597→  return [...staticEntries, ...productEntries]
  1598→}
  1599→```
  1600→
  1601→**Pitfalls**:
  1602→- Don't list redirect routes (302/301) — sitemaps must be 200-OK.
  1603→- Don't list routes that 404 (e.g., La Lounge product slugs if La Lounge has no product page).
  1604→- Include hreflang alternates via `alternates.languages`.
  1605→
  1606→### 8.8 robots.txt
  1607→
  1608→Use `src/app/robots.ts` (NOT a static `public/robots.txt`). The static file shadows the
  1609→generated one:
  1610→
  1611→```ts
  1612→export default function robots(): MetadataRoute.Robots {
  1613→  const baseUrl = process.env.NEXT_PUBLIC_SITE_URL || 'http://localhost:3000'
  1614→  return {
  1615→    rules: { userAgent: '*', disallow: ['/admin', '/api', '/checkout'] },
  1616→    sitemap: `${baseUrl}/sitemap.xml`,
  1617→  }
  1618→}
  1619→```
  1620→
  1621→**Pitfall**: If both `public/robots.txt` and `src/app/robots.ts` exist, the static file wins
  1622→and the dynamic rules are ignored. Delete the static file.
  1623→
  1624→### 8.9 JSON-LD Structured Data
  1625→
  1626→Emit `Organization` + `WebSite` schema on the HOME page only (not every route — it causes
  1627→duplicate competing schemas). Use `env`-aware URLs:
  1628→
  1629→```tsx
  1630→<JsonLd schema={{

  1641→## 9. Common Pitfalls Catalog
  1642→
  1643→This is the single most valuable section. Each entry maps a concrete symptom to its root
  1644→cause and exact fix. These are real bugs found in production code.
  1645→
  1646→### 9.1 Next.js 16 Pitfalls
  1647→
  1648→| Symptom | Root Cause | Fix |
  1649→|---------|-----------|-----|
  1650→| Page params are `undefined` | Used sync `params` signature | Change to `params: Promise<{...}>` + `await params` |
  1651→| Build error: "two pages resolve to same path" | Route group conflict | Only one `page.tsx` per URL; use redirects for alternates |
  1652→| `global-error.tsx` never triggers | Placed in `[locale]/` not root | Move to `src/app/global-error.tsx` |
  1653→| `middleware.ts` conflicts with `proxy.ts` | Next.js 16 renamed middleware | Delete `middleware.ts`, use `proxy.ts` |
  1654→| Hydration mismatch on dates/times | `Date.now()` in render | Move to `useEffect` |
  1655→| Theme flash (FOUC) on brand switch | SSR'd `data-brand` is hardcoded | Let client `BrandThemeSetter` set it; use `suppressHydrationWarning` |
  1656→
  1657→### 9.2 Security Pitfalls
  1658→
  1659→| Symptom | Root Cause | Fix |
  1660→|---------|-----------|-----|
  1661→| Admin route accessible without login | Missing `requireAuth()` in server action | Add as first statement in every admin action |
  1662→| Webhook processed twice | No idempotency check | Store nonce in `IdempotencyKey` table inside Serializable tx |
  1663→| Stock exhausted by spam | PENDING bookings never expire | Filter PENDING older than 30min TTL in availability queries |
  1664→| Price manipulated client-side | Client-supplied total trusted | Recompute total server-side in Serializable tx |
  1665→| Exact stock count leaked | Error message includes `${availableStock}` | Use generic "insufficient stock" message |
  1666→| Dev mock endpoint works in prod | No `NODE_ENV` guard | `if (NODE_ENV === 'production') return 404` |
  1667→| Slug race condition | `findFirst` + `create` not atomic | Catch P2002 → return `slug_exists` |
  1668→| Session cookie stolen via XSS | Missing `httpOnly` | Set `httpOnly: true, secure: true, sameSite: 'lax'` |
  1669→
  1670→### 9.3 Database Pitfalls
  1671→
  1672→| Symptom | Root Cause | Fix |
  1673→|---------|-----------|-----|
  1674→| Slow admin dashboard queries | Missing compound indexes | Add `@@index([brand, status])` etc. |
  1675→| Double-booking | Stock check + create in separate transactions | Interleave in one Serializable tx |
  1676→| Multi-day vs same-day overlap bug | Asymmetric +24h extension | Extend end date on BOTH request and stored |
  1677→| Orphaned bookings when product deleted | Missing `onDelete` | Add `onDelete: SetNull` (nullable FK) |
  1678→| Two different DB files | Path resolution mismatch | Use absolute path or consistent relative path |
  1679→| Stale Prisma client | Schema changed but not regenerated | Run `bunx prisma generate` (client only); `db:push` if the dev DB itself is stale |
  1680→| Float money drift | `Float` type for currency | Use `Decimal` (or `Float` + `KWD_TOLERANCE`) |
  1681→| Full table scan on admin search | No index on `ip`/`userId` | Add `@@index([ip])`, `@@index([userId])` |
  1682→| Multi-item order only confirms first booking | `orderId` is `bookings[0].id` | Generate shared `ORD-...` orderId; updateMany all siblings |

  1684→### 9.4 Code Quality Pitfalls
  1685→
  1686→| Symptom | Root Cause | Fix |
  1687→|---------|-----------|-----|
  1688→| Component crashes on null | `value!` non-null assertion | Explicit null check |

  1690→| Silent failure, no error | `catch (e) {}` | `console.error` + surface to user |

  1696→| Props accepted but ignored | Interface has unused fields | Remove + update all call sites |
  1697→| `MISSING_MESSAGE` error | Dynamic i18n key has no translation | `t.has(key) ? t(key) : fallback` |

  1757→## 10. The Loops Audit Methodology
  1758→
  1759→This methodology was used to find and fix 84 issues in a production codebase. It consists of
  1760→two agent groups iterating until zero issues remain, followed by a final 6-reviewer panel.
  1761→
  1762→### 10.1 Group 1: Analysis (Read-Only)
  1763→
  1764→Launch 4 parallel agents, each specialized in one domain. They READ and ANALYZE — they do
  1765→NOT fix anything.
  1766→
  1767→| Agent | Domain | Scope |
  1768→|-------|--------|-------|
  1769→| G1-A | Security | API routes, auth, webhooks, payment, admin guards, secrets |
  1770→| G1-B | Code Quality | Lib files, components, TypeScript strictness, React patterns |
  1771→| G1-C | Architecture | Routing, layouts, Next.js 16 specifics, SEO, performance |
  1772→| G1-D | Data & i18n | Prisma schema, queries, transactions, i18n parity |
  1773→
  1774→Each agent:
  1775→1. Reads the worklog to understand prior context.
  1776→2. Reads EVERY file in their scope (in full, no skimming).
  1777→3. Cites exact file:line and quotes problematic code.
  1778→4. Rates severity: CRITICAL / HIGH / MEDIUM / LOW / INFO.
  1779→5. Provides a concrete recommended fix.
  1780→6. Writes findings to a shared `audit-round-N.md` (append mode).
  1781→7. Returns a summary: total issues by severity + top 5 findings.
  1782→
  1783→**Output**: A consolidated, prioritized issue list.
  1784→
  1785→### 10.2 Group 2: Fixers (Write)
  1786→
  1787→Launch parallel fix agents. Each owns a set of files (no overlap — prevents conflicts).
  1788→Each reads the audit findings for their domain and applies surgical fixes.
  1789→
  1790→| Agent | Files Owned |
  1791→|-------|-------------|
  1792→| G2-1 | Architecture: layouts, sitemap, robots, not-found, global-error, next.config |
  1793→| G2-2 | API + booking logic: orders route, products.ts, webhooks, admin actions |
  1794→| G2-3 | Components: brand-colors, cart-button, product-card, admin components, 3D backgrounds |
  1795→| G2-4 | Schema + i18n: prisma/schema.prisma, messages/*.json |
  1796→
  1797→Each fixer:
  1798→1. Reads the worklog + audit findings.
  1799→2. Makes MINIMAL, surgical changes (no refactoring).
  1800→3. Preserves existing patterns.
  1801→4. Runs `bun run lint` + `tsc --noEmit` after edits.
  1802→5. Appends a worklog entry.
  1803→6. Returns a summary of fixes.
  1804→
  1805→### 10.3 Round 2: Re-Verification (Group 1 Again)
  1806→
  1807→The same 4 analysis agents re-verify. For each original issue:
  1808→- **FIXED** — fix is correct and complete (quote the fixed code).
  1809→- **PARTIALLY FIXED** — main issue resolved but edge cases remain.
  1810→- **NOT FIXED** — the fix didn't work or wasn't applied.
  1811→
  1812→Also check for NEW issues introduced by the parallel fixes (regressions).
  1813→
  1814→**Loop condition**: If any agent reports FAIL (blocking issues remain), go back to Group 2
  1815→for another fix round. Repeat until all 4 agents PASS.
  1816→
  1817→### 10.4 Group 3: Final 6-Reviewer Panel
  1818→
  1819→Once Groups 1 + 2 converge (zero blocking issues), launch 6 reviewers for a FRESH, deep
  1820→audit. They don't just verify fixes — they hunt for issues the first round missed.
  1821→
  1822→| Reviewer | Domain |
  1823→|----------|--------|
  1824→| R1 | Security & Authentication |
  1825→| R2 | Booking & Business Logic |
  1826→| R3 | Architecture & Next.js 16 |
  1827→| R4 | TypeScript & Code Quality |
  1828→| R5 | Data Integrity & i18n |
  1829→| R6 | UI/UX & Accessibility |
  1830→
  1831→Each reviewer:
  1832→1. Reads the worklog + all prior audit rounds.
  1833→2. Does a FRESH analysis (not just verifying fixes).
  1834→3. Hunts for issues the first round may have missed.
  1835→4. Returns PASS or FAIL with blocking issues.
  1836→
  1837→**Loop condition**: If any reviewer FAILS, go back to Group 2 for fixes, then re-verify.
  1838→Repeat until all 6 reviewers PASS.
  1839→
  1840→### 10.5 Why This Works
  1841→
  1842→1. **Separation of concerns**: Analysis agents have no incentive to "fix and move on" — they
  1843→   find issues deeply. Fix agents have clear file ownership — no merge conflicts.
  1844→2. **Fresh eyes**: Group 3 reviewers haven't seen the code before — they catch what
  1845→   round 1 normalized.
  1846→3. **Forced convergence**: The loop condition (all PASS) prevents declaring victory
  1847→   prematurely.
  1848→4. **Documented trail**: Every finding, fix, and verification is in the worklog — full
  1849→   auditability.
  1850→
  1851→### 10.6 Severity Definitions
  1852→
  1853→| Severity | Definition | Action |
  1854→|----------|-----------|--------|
  1855→| CRITICAL | Exploitable / data loss / crash / RCE / auth bypass | Fix immediately; blocks release |
  1856→| HIGH | Likely bug / privilege escalation / data leak / SEO loss | Fix before release |
  1857→| MEDIUM | Code smell / inconsistency / defense-in-depth gap | Fix in next sprint |
  1858→| LOW | Minor improvement / hardening | Backlog |
  1859→| INFO | Observation / positive finding | Note only |
