    99→    99→### 1.3 Next.js 16 Specifics (Critical — These Changed)
   100→   100→
   101→   101→#### `params` and `searchParams` are now Promises
   102→   102→In Next.js 16, every page that receives `params` or `searchParams` MUST await them. The old
   103→   103→synchronous signature silently breaks or causes type errors.
   104→   104→
   105→   105→```tsx
   106→   106→// ✅ CORRECT (Next.js 16)
   107→   107→export default async function ProductPage({
   108→   108→  params,
   109→   109→}: {
   110→   110→  params: Promise<{ locale: string; slug: string }>
   111→   111→}) {
   112→   112→  const { locale, slug } = await params
   113→   113→  // ...
   114→   114→}
   115→   115→
   116→   116→// ❌ WRONG (Next.js 15 and earlier — will break)
   117→   117→export default function ProductPage({ params }: { params: { slug: string } }) {
   118→   118→  const { slug } = params
   119→   119→}
   120→   120→```
   121→   121→
   122→   122→#### `proxy.ts` replaces `middleware.ts`
   123→   123→Next.js 16 renamed `middleware.ts` to `proxy.ts`. **Never** create `src/middleware.ts` — it
   124→   124→will conflict with `proxy.ts` and cause build failures. If you see a stale `middleware.ts`,
   125→   125→delete it and add it to `.gitignore`.
   126→   126→
   127→   127→#### `cookies()` and `headers()` are now async
   128→   128→Since Next.js 15, `cookies()` and `headers()` (from `next/headers`) return Promises. You must
   129→   129→`await` them — calling `.get()` on the Promise directly is a type error and a runtime crash:
   130→   130→
   131→   131→```ts
   132→   132→import { cookies } from 'next/headers'
   133→   133→
   134→   134→// ✅ CORRECT
   135→   135→const store = await cookies()
   136→   136→const session = store.get('session')
   137→   137→
   138→   138→// ❌ WRONG (Next.js 14 style — breaks on 15+)
   139→   139→const session = cookies().get('session')
   140→   140→```
   141→   141→
   142→   142→Note: `store.set()` only works inside Server Actions and Route Handlers — never during a
   143→   143→page render.
   144→   144→
   145→   145→#### `global-error.tsx` location
   146→   146→`global-error.tsx` is only honored at `src/app/global-error.tsx` (the root). Placing it
   147→   147→inside `[locale]/` makes it dead code. It must render its own `<html>` and `<body>`:
   148→   148→
   149→   149→```tsx
   150→   150→'use client'
   151→   151→export default function GlobalError({ error, reset }: { error: Error; reset: () => void }) {
   152→   152→  return (
   153→   153→    <html lang="en">
   154→   154→      <body>
   155→   155→        <h2>Something went wrong!</h2>
   156→   156→        <button onClick={() => reset()}>Try again</button>
   157→   157→      </body>
   158→   158→    </html>
   159→   159→  )
   160→   160→}
   161→   161→```
   162→   162→
   163→   163→### 1.4 Route Group Pitfalls
   164→   164→
   165→   165→Route groups `(name)` do NOT affect the URL. Two files at the same effective path cause a
   166→   166→build-time "two parallel pages that resolve to the same path" error:
   167→   167→
   168→   168→```
   169→   169→src/app/[locale]/admin/page.tsx              → /admin
   170→   170→src/app/[locale]/admin/(dashboard)/page.tsx  → /admin   ← CONFLICT!
   171→   171→```
   172→   172→
   173→   173→**Rule**: Only ONE page.tsx may resolve to any given URL. Use route groups for layout
   174→   174→grouping, not for alternate page content. If you need a "landing vs dashboard" split,
   175→   175→redirect from one to the other:
   176→   176→
   177→   177→```tsx
   178→   178→// src/app/[locale]/admin/page.tsx
   179→   179→import { redirect } from 'next/navigation'
   180→   180→export default function AdminEntry() {
   181→   181→  redirect('/admin/dashboard')  // or to login if unauthenticated
   182→   182→}
   183→   183→```
   184→   184→
   185→   185→### 1.5 Server vs Client Component Boundaries
   186→   186→
   187→   187→Mark a component `'use client'` ONLY when it needs:
   188→   188→- `useState`, `useEffect`, `useReducer`, context
   189→   189→- Event handlers (`onClick`, etc.)
   190→   190→- Browser APIs (`window`, `localStorage`, `navigator`)
   191→   191→- `usePathname`, `useRouter`, `useSearchParams`
   192→   192→
   193→   193→**Anti-pattern**: A `'use client'` component that imports `@/lib/db` or `fs`. This bloats
   194→   194→the client bundle and leaks server code. Instead, fetch data in a server component and pass
   195→   195→it as serializable props to a client child.
   196→   196→
   197→   197→**Anti-pattern**: A server component using hooks. It will crash at runtime.
   198→   198→
   199→   199→**Heavy library rule**: Three.js, Chart.js, and any library >50KB should be dynamically
   200→   200→imported with `{ ssr: false }` when used in client components:
   201→   201→
   202→   202→```tsx
   203→   203→const Heavy3D = dynamic(() => import('./heavy-3d'), {
   204→   204→  ssr: false,
   205→   205→  loading: () => <div className="fixed inset-0 -z-10 bg-background" />, // ← NEVER null
   206→   206→})
   207→   207→```
   208→   208→
   209→   209→### 1.6 Hydration Safety
   210→   210→
   211→   211→Anything that differs between server and client renders causes a hydration mismatch
   212→   212→warning (or crash). The classic traps:
   213→   213→
   214→   214→| Trap | Fix |
   215→   215→|------|-----|
   216→   216→| `Date.now()`, `Math.random()` in render | Move to `useEffect` |
   217→   217→| `typeof window !== 'undefined'` checks | Use `useEffect` + state instead |
   218→   218→| `localStorage` / `sessionStorage` in render | Gate with `useEffect` + `mounted` state |
   219→   219→| Timezone-dependent date formatting | Format on the client only, after mount |
   220→   220→| `window.matchMedia('(prefers-reduced-motion)')` in render | Use a `mounted` flag |
   221→   221→
   222→   222→```tsx
   223→   223→// ✅ Safe hydration guard pattern
   224→   224→const [mounted, setMounted] = useState(false)
   225→   225→useEffect(() => setMounted(true), [])
   226→   226→if (!mounted) return <Skeleton />  // server + first paint
   227→   227→return <RealContent />              // client only
   228→   228→```
   229→   229→
   230→   230→### 1.7 Layout Hierarchy & Sticky Footer
   231→   231→
   232→   232→The root locale layout MUST establish the sticky-footer pattern so short pages push the
   233→   233→footer to the viewport bottom and long pages push it down naturally:
   234→   234→
   235→   235→```tsx
   236→   236→// src/app/[locale]/layout.tsx
   237→   237→<body className="min-h-screen flex flex-col">
   238→   238→  <Navbar />
   239→   239→  <main className="flex-1">{children}</main>
   240→   240→  <Footer className="mt-auto" />
   241→   241→</body>
   242→   242→```
   243→   243→
   244→   244→- `min-h-screen flex flex-col` on the body makes it at least viewport-height and a flex column.
   245→   245→- `flex-1` on `<main>` grows to fill available space.
   246→   246→- `mt-auto` on `<footer>` pushes it to the bottom when content is short.
   247→   247→- For iOS safe area: add `pb-[env(safe-area-inset-bottom)]` to the footer.
   248→   248→
   249→   249→### 1.8 Loading, Error, and Not-Found Files
   250→   250→
   251→   251→Every route segment that does async work should have:
   252→   252→- `loading.tsx` — skeleton or spinner with `role="status"` + `aria-live="polite"` + `sr-only` text
   253→   253→- `error.tsx` — user-friendly message + retry button (never show stack traces)
   254→   254→- `not-found.tsx` — for 404s specific to this segment
   255→   255→
   256→   256→```tsx
   257→   257→// loading.tsx
   258→   258→export default function Loading() {
   259→   259→  return (
   260→   260→    <div role="status" aria-live="polite" className="flex items-center justify-center py-20">
   261→   261→      <Loader2 className="size-6 animate-spin" />
   262→   262→      <span className="sr-only">Loading…</span>
   263→   263→    </div>
   264→   264→  )
   265→   265→}
   266→   266→```
   267→   267→
   268→   268→```tsx
   269→   269→// not-found.tsx (server component — use getTranslations, NOT useTranslations)
   270→   270→import { getTranslations } from 'next-intl/server'
   271→   271→export default async function NotFound() {
   272→   272→  const t = await getTranslations()
   273→   273→  return <h1>{t('notFound.title')}</h1>
   274→   274→}
   275→   275→```
   276→   276→
   277→   277→> **Critical pitfall**: `not-found.tsx` renders when `notFound()` is called, which can happen
   278→   278→> BEFORE the i18n provider is mounted (e.g., invalid locale). Using `useTranslations()` (a
   279→   279→> client hook) in a server `not-found.tsx` will throw. Always use `getTranslations()` (the
   280→   280→> server-side async version).

   284→   284→## 2. Security Hardening
   285→   285→
   286→   286→### 2.1 Authentication Architecture
   287→   287→
   288→   288→Use a **two-layer defense-in-depth** model:
   289→   289→
   290→   290→1. **Edge layer** (`src/proxy.ts`): HMAC-verified session cookie check. Runs before SSR.
   291→   291→   Redirects unauthenticated users to `/login` for admin routes.
   292→   292→2. **Server layer** (`requireAuth()` in every server action / admin page): Re-verifies the
   293→   293→   session in Node. This catches any edge-layer bypass and is your real source of truth.
   294→   294→
   295→   295→```ts
   296→   296→// src/lib/auth.ts
   297→   297→import { cookies } from 'next/headers'
   298→   298→
   299→   299→export async function requireAuth() {
   300→   300→  const store = await cookies()          // cookies() is async since Next.js 15
   301→   301→  const session = store.get('session')
   302→   302→  if (!session) throw new Error('UNAUTHORIZED')
   303→   303→  const payload = await verifySession(session.value)  // HMAC verify
   304→   304→  if (!payload) throw new Error('INVALID_SESSION')
   305→   305→  return payload  // { userId, role, brand, ... }
   306→   306→}
   307→   307→```
   308→   308→
   309→   309→**Rule**: Every admin server action MUST call `requireAuth()` as its first statement. No
   310→   310→exceptions. Do not rely on "the layout checks it" — defense in depth.
   311→   311→
   312→   312→### 2.2 Input Validation
   313→   313→
   314→   314→Validate EVERY API input before it reaches Prisma. Use Zod:
   315→   315→
   316→   316→```ts
   317→   317→import { z } from 'zod'
   318→   318→
   319→   319→const CreateOrderSchema = z.object({
   320→   320→  items: z.array(z.object({
   321→   321→    productId: z.string().min(1),
   322→   322→    quantity: z.number().int().positive().max(100),
   323→   323→    startDate: z.string().datetime(),
   324→   324→    endDate: z.string().datetime(),
   325→   325→  })).min(1).max(50),
   326→   326→  customerName: z.string().min(2).max(100),
   327→   327→  customerPhone: z.string().min(5).max(20),
   328→   328→})
   329→   329→
   330→   330→export async function POST(req: Request) {
   331→   331→  const body = await req.json()
   332→   332→  const parsed = CreateOrderSchema.safeParse(body)
   333→   333→  if (!parsed.success) {
   334→   334→    return NextResponse.json({ error: 'invalid_input', details: parsed.error.flatten() }, { status: 400 })
   335→   335→  }
   336→   336→  // Use parsed.data — it's now type-safe and validated
   337→   337→}
   338→   338→```
   339→   339→
   340→   340→### 2.3 SQL/NoSQL Injection
   341→   341→
   342→   342→Prisma's query builder is parameterized by default — safe from injection. The danger zones:
   343→   343→
   344→   344→- `Prisma.raw()` / `$queryRawUnsafe()` — NEVER interpolate user input.
   345→   345→- Dynamic `orderBy` from user input — validate against an allow-list.
   346→   346→- Dynamic field names in `select`/`where` — validate against an allow-list.
   347→   347→
   348→   348→```ts
   349→   349→// ❌ DANGEROUS
   350→   350→const orderBy = req.nextUrl.searchParams.get('sort')!
   351→   351→const products = await db.product.findMany({ orderBy: { [orderBy]: 'asc' } })
   352→   352→
   353→   353→// ✅ SAFE
   354→   354→const ALLOWED_SORTS = ['name', 'price', 'createdAt'] as const
   355→   355→const sort = ALLOWED_SORTS.find(s => s === req.nextUrl.searchParams.get('sort')) ?? 'createdAt'
   356→   356→const products = await db.product.findMany({ orderBy: { [sort]: 'asc' } })
   357→   357→```
   358→   358→
   359→   359→### 2.4 Webhook Security
   360→   360→
   361→   361→Webhooks (payment callbacks, etc.) are a prime attack surface. Three layers of defense:
   362→   362→
   363→   363→1. **HMAC signature verification** — verify the request actually came from the claimed sender.
   364→   364→2. **Timestamp skew check** — reject requests older than 5 minutes (replay protection).
   365→   365→3. **Nonce / idempotency key** — store the nonce in a DB table inside the transaction; reject
   366→   366→   duplicates.
   367→   367→
   368→   368→```ts
   369→   369→// Webhook verification
   370→   370→const signature = req.headers.get('x-webhook-signature')  // hmac(rawBody + timestamp + nonce)
   371→   371→const timestamp = req.headers.get('x-webhook-timestamp')
   372→   372→const nonce = req.headers.get('x-webhook-nonce')
   373→   373→
   374→   374→// 1. Skew check (replay protection)
   375→   375→const skew = Math.abs(Date.now() - Number(timestamp))
   376→   376→if (skew > 5 * 60 * 1000) return NextResponse.json({ error: 'stale' }, { status: 401 })
   377→   377→
   378→   378→// 2. HMAC verify (constant-time comparison!)
   379→   379→// In a Node-runtime route handler, use node:crypto (NOT crypto.subtle — see note below):
   380→   380→import { createHmac, timingSafeEqual } from 'node:crypto'
   381→   381→const expected = createHmac('sha256', WEBHOOK_SECRET)
   382→   382→  .update(rawBody + timestamp + nonce)
   383→   383→  .digest('hex')
   384→   384→const sigBuf = Buffer.from(signature, 'hex')
   385→   385→const expBuf = Buffer.from(expected, 'hex')
   386→   386→if (sigBuf.length !== expBuf.length || !timingSafeEqual(sigBuf, expBuf)) {
   387→   387→  return NextResponse.json({ error: 'invalid_sig' }, { status: 401 })
   388→   388→}
   389→   389→
   390→   390→// 3. Nonce uniqueness (inside the Serializable transaction)
   391→   391→await db.$transaction(async (tx) => {
   392→   392→  await tx.idempotencyKey.create({ data: { key: nonce, expiresAt: new Date(Date.now() + 86400000) } })
   393→   393→  // ... process webhook ...
   394→   394→}, { isolationLevel: 'Serializable' })  // ← catches concurrent duplicate nonces
   395→   395→```
   396→   396→
   397→   397→**Constant-time comparison**: Use `timingSafeEqual` from `node:crypto` on equal-length
   398→   398→Buffers. **There is no `crypto.subtle.timingSafeEqual`** — that API does not exist in Web
   399→   399→Crypto (a common AI-generated hallucination; it fails at runtime). On Edge runtime, use a
   400→   400→custom constant-time XOR comparison. Never `===` for secret comparison — it leaks
   401→   401→length/timing info.
   402→   402→
   403→   403→### 2.5 Rate Limiting
   404→   404→
   405→   405→Rate-limit ALL sensitive endpoints: login, contact form, checkout, password reset.
   406→   406→
   407→   407→```ts
   408→   408→// src/lib/rate-limiter.ts
   409→   409→const RATE_LIMIT = { windowMs: 60_000, max: 10 }  // 10 req/min/IP
   410→   410→
   411→   411→export async function rateLimit(ip: string, route: string) {
   412→   412→  const key = `${route}:${ip}`
   413→   413→  const entry = cache.get(key) ?? { count: 0, resetAt: Date.now() + RATE_LIMIT.windowMs }
   414→   414→  if (Date.now() > entry.resetAt) {
   415→   415→    entry.count = 0
   416→   416→    entry.resetAt = Date.now() + RATE_LIMIT.windowMs
   417→   417→  }
   418→   418→  entry.count++
   419→   419→  cache.set(key, entry)
   420→   420→  if (entry.count > RATE_LIMIT.max) {
   421→   421→    throw new RateLimitError(entry.resetAt)
   422→   422→  }
   423→   423→}
   424→   424→```
   425→   425→
   426→   426→**IP extraction pitfall**: `X-Forwarded-For` can be spoofed. If behind a trusted proxy
   427→   427→(Caddy, Cloudflare), take the LAST IP in the chain or use the proxy-specific header
   428→   428→(`CF-Connecting-IP`, `X-Real-IP`). Never trust a client-supplied `X-Forwarded-For` directly.
   429→   429→
   430→   430→**Multi-instance warning**: The in-memory `cache` above is per-process. On serverless or
   431→   431→multi-instance deployments, each instance keeps its own counter — the effective limit
   432→   432→multiplies by the instance count. Back the limiter with shared storage (Redis / Upstash:
   433→   433→atomic `INCR` + `EXPIRE`) whenever you scale beyond one instance.
   434→   434→
   435→   435→### 2.6 Secrets Management
   436→   436→
   437→   437→- ALL secrets live in `.env` (or environment variables in production). Never hardcoded.
   438→   438→- The `NEXT_PUBLIC_` prefix makes a var available in the client bundle. **Only** use it for
   439→   439→  truly public values (`NEXT_PUBLIC_SITE_URL`, `NEXT_PUBLIC_GA_ID`). Secrets like
   440→   440→  `DATABASE_URL`, `PAYMENT_SECRET`, `JWT_SECRET` must NEVER have the `NEXT_PUBLIC_` prefix.
   441→   441→- Validate secrets at startup — fail closed if missing or too short:
   442→   442→
   443→   443→```ts
   444→   444→function getSecret(name: string): string {
   445→   445→  const val = process.env[name]
   446→   446→  if (!val) throw new Error(`Missing env var: ${name}`)
   447→   447→  if (val.length < 32) throw new Error(`${name} must be at least 32 chars`)
   448→   448→  return val
   449→   449→}
   450→   450→```
   451→   451→
   452→   452→### 2.7 IDOR (Insecure Direct Object Reference)
   453→   453→
   454→   454→Any endpoint that takes an ID (`/api/orders/[id]`, `/api/bookings/[id]`) MUST verify the
   455→   455→requester owns that resource:
   456→   456→
   457→   457→```ts
   458→   458→export async function GET(req: Request, { params }: { params: Promise<{ id: string }> }) {
   459→   459→  const { id } = await params
   460→   460→  const session = await requireAuth()
   461→   461→  const order = await db.order.findFirst({
   462→   462→    where: { id, userId: session.userId },  // ← scope to owner
   463→   463→  })
   464→   464→  if (!order) return NextResponse.json({ error: 'not_found' }, { status: 404 })
   465→   465→}
   466→   466→```
   467→   467→
   468→   468→Admin endpoints should scope by brand, not by user — but still verify the admin has access
   469→   469→to that brand.
   470→   470→
   471→   471→### 2.8 Cookie Security
   472→   472→
   473→   473→Session cookies MUST have:
   474→   474→- `httpOnly: true` — prevents JavaScript access (XSS protection)
   475→   475→- `secure: true` — HTTPS only (in production)
   476→   476→- `sameSite: 'lax'` — CSRF protection (or `'strict'` for maximum security)
   477→   477→- `__Host-` prefix — binds the cookie to the host (no subdomain sharing)
   478→   478→
   479→   479→```ts
   480→   480→// Must run inside a Server Action or Route Handler (set() is not allowed during renders)
   481→   481→const store = await cookies()  // async since Next.js 15
   482→   482→store.set('session', token, {
   483→   483→  httpOnly: true,
   484→   484→  secure: process.env.NODE_ENV === 'production',
   485→   485→  sameSite: 'lax',
   486→   486→  path: '/',
   487→   487→  maxAge: 60 * 60 * 24,  // 24h — keep admin sessions short (policy: 24h max)
   488→   488→})
   489→   489→```
   490→   490→
   491→   491→### 2.9 Payment Integrity
   492→   492→
   493→   493→NEVER trust a client-supplied price. The server recomputes everything inside a Serializable
   494→   494→transaction:
   495→   495→
   496→   496→```ts
   497→   497→await db.$transaction(async (tx) => {
   498→   498→  // 1. Fetch the product (with a fresh read inside the tx)
   499→   499→  const product = await tx.product.findUniqueOrThrow({ where: { id } })
   500→   500→  
   501→   501→  // 2. Recompute days, totals
   502→   502→  const days = computeDays(startDate, endDate)
   503→   503→  const total = product.rentalPricePerDay * days * quantity
   504→   504→  
   505→   505→  // 3. Tolerance check (floating-point safety)
   506→   506→  if (Math.abs(total - clientSuppliedTotal) > 0.001) {
   507→   507→    throw new Error('PRICE_MISMATCH')
   508→   508→  }
   509→   509→  
   510→   510→  // 4. Create the booking
   511→   511→  await tx.booking.create({ data: { ... } })
   512→   512→}, { isolationLevel: 'Serializable' })
   513→   513→```
   514→   514→
   515→   515→### 2.10 Dev-Only Endpoints
   516→   516→
   517→   517→Mock/dev endpoints (test payment, debug routes) MUST be gated to non-production:
   518→   518→

   520→   520→export async function POST() {
   521→   521→  if (process.env.NODE_ENV === 'production') {
   522→   522→    return NextResponse.json({ error: 'not_found' }, { status: 404 })

   528→   528→### 2.11 Information Disclosure
   529→   529→
   530→   530→Error responses should NEVER leak:
   531→   531→- Stack traces (use a generic message in production, log full trace server-side)
   532→   532→- Internal file paths
   533→   533→- DB schema / table names
   534→   534→- Exact remaining stock counts (use generic "insufficient stock" messages)
   535→   535→
   536→   536→```ts
   537→   537→// ❌ LEAKS INFO
   538→   538→return NextResponse.json({ error: `Requested ${qty} but only ${available} left` }, { status: 409 })
   539→   539→
   540→   540→// ✅ SAFE
   541→   541→return NextResponse.json({ error: 'out_of_stock', message: 'Requested quantity exceeds available stock' }, { status: 409 })
   542→   542→```

   544→   544→### 2.12 Security Headers
   545→   545→
   546→   546→Set baseline security headers centrally in `next.config.ts` — they then apply to every route
   547→   547→(including API), with zero per-page effort:
   548→   548→
   549→   549→```ts
   550→   550→// next.config.ts
   551→   551→const securityHeaders = [
   552→   552→  { key: 'X-Content-Type-Options', value: 'nosniff' },
   553→   553→  { key: 'X-Frame-Options', value: 'DENY' },
   554→   554→  { key: 'Referrer-Policy', value: 'strict-origin-when-cross-origin' },
   555→   555→  { key: 'Permissions-Policy', value: 'camera=(), microphone=(), geolocation=()' },
   556→   556→  { key: 'Strict-Transport-Security', value: 'max-age=63072000; includeSubDomains; preload' },
   557→   557→  { key: 'Content-Security-Policy',
   558→   558→    value: "default-src 'self'; img-src 'self' data: blob: https:; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline'; frame-ancestors 'none'" },
   559→   559→]
   560→   560→
   561→   561→const nextConfig = {
   562→   562→  async headers() {
   563→   563→    return [{ source: '/:path*', headers: securityHeaders }]
   564→   564→  },
   565→   565→}
   566→   566→
   567→   567→export default nextConfig
   568→   568→```
   569→   569→
   570→   570→- Tighten the CSP progressively toward nonces/hashes. `'unsafe-inline'` on `script-src` is a
   571→   571→  last resort — acceptable at launch, not as the end state.
   572→   572→- Add HSTS only after confirming HTTPS is fully working on the production domain — it pins
   573→   573→  HTTPS permanently for returning visitors.
   574→   574→- Verify with securityheaders.com after every deployment; a missing header after a config
   575→   575→  rewrite is a classic silent regression.

   579→   579→## 3. Database & Prisma Patterns
   580→   580→
   581→   581→### 3.1 Schema Design Principles
   582→   582→
   583→   583→**Money**: Use `Decimal` (not `Float`) for monetary values. Float has ~15 significant digits
   584→   584→and accumulates rounding errors. If you MUST use Float (SQLite limitation), apply a
   585→   585→`KWD_TOLERANCE = 0.001` check in every aggregation.
   586→   586→
   587→   587→```prisma
   588→   588→model Product {
   589→   589→  rentalPricePerDay Decimal @db.Decimal(10, 3)  // 3 decimal places for KWD
   590→   590→}
   591→   591→```
   592→   592→
   593→   593→**Status fields**: Use enums, not strings:
   594→   594→
   595→   595→```prisma
   596→   596→enum BookingStatus {
   597→   597→  PENDING
   598→   598→  CONFIRMED
   599→   599→  CANCELLED
   600→   600→  COMPLETED
   601→   601→  PAYMENT_FAILED
   602→   602→}
   603→   603→
   604→   604→model Booking {
   605→   605→  status BookingStatus @default(PENDING)
   606→   606→}
   607→   607→```
   608→   608→
   609→   609→**Timestamps**: Always include `createdAt` and `updatedAt` with defaults:
   610→   610→
   611→   611→```prisma
   612→   612→model Booking {
   613→   613→  createdAt DateTime @default(now())
   614→   614→  updatedAt DateTime @updatedAt
   615→   615→}
   616→   616→```
   617→   617→
   618→   618→### 3.2 Indexes (Critical for Performance)
   619→   619→
   620→   620→Add compound indexes for every common query filter. Missing indexes cause full table scans
   621→   621→that kill performance at scale.
   622→   622→
   623→   623→```prisma
   624→   624→model Booking {
   625→   625→  brand      Brand       @default(LUT)
   626→   626→  status     BookingStatus @default(PENDING)
   627→   627→  productId  String?
   628→   628→  orderId    String?
   629→   629→  
   630→   630→  product    Product?    @relation(fields: [productId], references: [id], onDelete: SetNull)
   631→   631→  
   632→   632→  @@index([brand, status])           // admin dashboard filter
   633→   633→  @@index([productId, status])       // availability queries
   634→   634→  @@index([orderId])                // multi-item order grouping
   635→   635→  @@index([brand, isActive, createdAt])  // storefront "newest in brand" sort
   636→   636→}
   637→   637→```
   638→   638→
   639→   639→**Rule of thumb**: For every `findMany({ where: { a, b } })`, there should be an
   640→   640→`@@index([a, b])`. Foreign keys are NOT automatically indexed in SQLite — add them explicitly.
   641→   641→
   642→   642→### 3.3 Relations & onDelete
   643→   643→
   644→   644→Always declare `onDelete` behavior explicitly:
   645→   645→
   646→   646→| Setting | Use when |
   647→   647→|---------|----------|
   648→   648→| `Cascade` | Child can't exist without parent (e.g., OrderItem → Order) |
   649→   649→| `SetNull` | Child should survive parent deletion (e.g., Booking → Product; booking history stays) |
   650→   650→| `Restrict` | Prevent deletion if children exist (e.g., can't delete a Product with active bookings) |
   651→   651→| `NoAction` | Default — DB decides (usually same as Restrict) |
   652→   652→
   653→   653→```prisma
   654→   654→model Booking {
   655→   655→  productId String?
   656→   656→  product   Product? @relation(fields: [productId], references: [id], onDelete: SetNull)
   657→   657→}
   658→   658→```
   659→   659→
   660→   660→The FK field must be nullable (`String?`) for `SetNull` to work.
   661→   661→
   662→   662→### 3.4 Multi-Tenant Isolation
   663→   663→
   664→   664→If your app has multiple tenants (brands, organizations), every tenant-scoped model MUST
   665→   665→have a `brand` (or `tenantId`) field. Every query MUST filter by it:
   666→   666→
   667→   667→```ts
   668→   668→// ✅ Correct — always scope by brand
   669→   669→export async function getProducts({ brand, ... }: { brand: Brand }) {
   670→   670→  return db.product.findMany({ where: { brand, isActive: true } })
   671→   671→}
   672→   672→```
   673→   673→
   674→   674→Admin queries use `getAdminBrand()` to determine which brand the admin is managing:
   675→   675→
   676→   676→```ts
   677→   677→export async function adminGetProducts(adminSession: Session) {
   678→   678→  const brand = adminSession.brand  // from the session, not the URL
   679→   679→  return db.product.findMany({ where: { brand } })
   680→   680→}
   681→   681→```
   682→   682→
   683→   683→**Pitfall**: A product lookup by ID alone (no brand filter) is acceptable IF the ID is a
   684→   684→unguessable cuid. But availability checks should still scope by brand for defense-in-depth.
   685→   685→
   686→   686→### 3.5 Transactions & Concurrency
   687→   687→
   688→   688→Multi-step writes MUST be in a transaction. Booking/stock operations need `Serializable`
   689→   689→isolation to prevent race conditions:
   690→   690→
   691→   691→```ts
   692→   692→await db.$transaction(async (tx) => {
   693→   693→  // 1. Check availability (fresh read inside tx)
   694→   694→  const available = await checkStockAvailabilityInTx(tx, productId, startDate, endDate)
   695→   695→  if (available < quantity) throw new Error('OUT_OF_STOCK')
   696→   696→  
   697→   697→  // 2. Create booking (within the same tx — next check sees this)
   698→   698→  await tx.booking.create({ data: { ... } })
   699→   699→}, { isolationLevel: 'Serializable' })
   700→   700→```
   701→   701→
   702→   702→**Critical**: The stock check and the booking create MUST be in the same transaction. If they
   703→   703→are in separate transactions (or sequential queries), two concurrent requests can both pass
   704→   704→the check and both create bookings → **overbooking**.
   705→   705→
   706→   706→### 3.6 Booking Overlap Detection
   707→   707→
   708→   708→The hardest part of any rental system. The overlap condition is:
   709→   709→
   710→   710→```
   711→   711→A booking overlaps B if: A.start < B.end AND A.end > B.start
   712→   712→```
   713→   713→
   714→   714→For same-day rentals (where `start === end`), you MUST extend the effective end date by 24h
   715→   715→on BOTH sides, or multi-day vs same-day comparisons break:
   716→   716→
   717→   717→```ts
   718→   718→// ✅ Symmetric overlap detection
   719→   719→function overlaps(requestStart: Date, requestEnd: Date, storedStart: Date, storedEnd: Date): boolean {
   720→   720→  // Extend end dates to end-of-day for both request and stored
   721→   721→  const requestEffectiveEnd = endOfDay(requestEnd)
   722→   722→  const storedEffectiveEnd = endOfDay(storedEnd)
   723→   723→  
   724→   724→  return requestStart < storedEffectiveEnd && storedStart < requestEffectiveEnd
   725→   725→}
   726→   726→
   727→   727→function endOfDay(d: Date): Date {
   728→   728→  const copy = new Date(d)
   729→   729→  copy.setUTCHours(23, 59, 59, 999)
   730→   730→  return copy
   731→   731→}
   732→   732→```
   733→   733→
   734→   734→**The asymmetric bug — concrete example**: A customer tries to book a same-day rental on
   735→   735→Aug 5 (`start = end = Aug 5 00:00`). Another user already holds a multi-day booking
   736→   736→Aug 1–5, whose `end` is stored as `Aug 5 00:00` (NOT extended). The overlap check:
   737→   737→`request.start (Aug 5 00:00) < stored.effectiveEnd (Aug 5 00:00)` → **false** → no overlap
   738→   738→detected → double-booking on a day the existing booking actually owns. Extending BOTH
   739→   739→sides to end-of-day catches it: `Aug 5 00:00 < Aug 5 23:59.999` → true. The rule:
   740→   740→**always extend both sides** and use strict `<` — never extend only the request, never only
   741→   741→the stored booking, and never mix `<` with `<=` across the two comparisons.
   742→   742→
   743→   743→### 3.7 PENDING Booking Expiry
   744→   744→
   745→   745→If your system has a PENDING state (booking created, awaiting payment), PENDING bookings
   746→   746→lock stock indefinitely unless they expire. This is a DoS vector — an attacker can spam
   747→   747→PENDING bookings to exhaust all stock.
   748→   748→
   749→   749→**Fix**: Filter out PENDING bookings older than a TTL (e.g., 30 minutes) in availability
   750→   750→queries:
   751→   751→
   752→   752→```ts
   753→   753→const PENDING_BOOKING_TTL_MS = 30 * 60 * 1000
   754→   754→
   755→   755→export async function checkStockAvailability(productId: string, start: Date, end: Date) {
   756→   756→  const activeBookings = await db.booking.findMany({
   757→   757→    where: {
   758→   758→      productId,
   759→   759→      OR: [
   760→   760→        { status: { in: ['CONFIRMED', 'COMPLETED'] } },
   761→   761→        { status: 'PENDING', createdAt: { gte: new Date(Date.now() - PENDING_BOOKING_TTL_MS) } },
   762→   762→      ],
   763→   763→      // overlap condition...
   764→   764→    },
   765→   765→  })
   766→   766→}
   767→   767→```
   768→   768→
   769→   769→This is "lazy GC" — no cron job needed. Stale PENDING bookings are simply ignored.
   770→   770→
   771→   771→### 3.8 Prisma Error Handling
   772→   772→
   773→   773→Catch specific Prisma error codes and return user-friendly messages:
   774→   774→
   775→   775→```ts
   776→   776→import { Prisma } from '@prisma/client'
   777→   777→
   778→   778→try {
   779→   779→  await db.product.create({ data: { ... } })
   780→   780→} catch (e) {
   781→   781→  if (e instanceof Prisma.PrismaClientKnownRequestError) {
   782→   782→    if (e.code === 'P2002') {
   783→   783→      // Unique constraint violation
   784→   784→      return { error: 'slug_exists' }
   785→   785→    }
   786→   786→    if (e.code === 'P2025') {
   787→   787→      // Record not found
   788→   788→      return { error: 'not_found' }
   789→   789→    }
   790→   790→    if (e.code === 'P2034') {
   791→   791→      // Transaction conflict (race condition)
   792→   792→      return { error: 'conflict_retry' }
   793→   793→    }
   794→   794→  }
   795→   795→  throw e  // re-throw unknown errors
   796→   796→}
   797→   797→```
   798→   798→
   799→   799→**TOCTOU fix**: The `findFirst` duplicate-check + `create` pattern is not atomic. Even if
   800→   800→you pre-check, a concurrent request can create the same record between check and create.
